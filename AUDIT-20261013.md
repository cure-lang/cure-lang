## 2. Verification: the previous audit's headline defects

The previous audit's most damaging findings were of the "documentation promises more
than the implementation delivers" kind. **Every one of them is now fixed and was
re-verified by running the compiler.**

### 2.1 ✅ FIXED — Macro containers now work with `cure check` and project `compile`

The old audit's #1 defect: every `fsm`/`actor`/`sup`/`app` container failed `cure check`
with a generic `E092`, and failed project-mode `cure compile` with an opaque
`module_identity_missing`.

**Re-verified now (freshly built escript):**

```
$ cure check fsm2.cure          → fsm2.cure: OK        (exit 0)
$ cure compile fsm2.cure        → -> Cure.Machine      (exit 0)
$ cure check lib/fsm.cure       → lib/fsm.cure: OK     (exit 0)
$ cure compile lib/             → -> Cure.Fsmproj, Cure.Fsmproj.Fsm   (exit 0)
$ cure run lib/main.cure        → hello from fsmproj   (exit 0)
$ cure test                     → 1 passed, 0 failed   (exit 0)
```

The whole `examples/cure_exchange/cure` project — the exact showcase the old audit
cited as broken — now **compiles in project mode and passes 33/33 tests**:

```
$ cure compile lib/   → Cure.Exchange.{Demo,Escrow,EscrowFsm,EscrowFsmDslReference,Ledger,Money,OtpDemo}
$ cure test           → 33 passed, 0 failed
```

And the officially scaffolded `cure new <name> --fsm` template now survives its own
printed "next steps" (check / compile / run / test all pass).

**Consequence (corrected):** `examples/cure_exchange/cure/README.md`'s "Known
limitations" section is **partly** stale. Empirically re-checked against this
tree, of its four items:

- **limitation 2 (`cure check` cannot validate an `fsm`) is FIXED** —
  `cure check lib/fsm.cure` now prints `OK` (exit 0), and project-mode
  `cure compile lib/` emits the generated module. The `cure new --fsm` template
  survives its own check / compile / run / test steps.
- **limitation 1 (calling a macro-generated submodule's API) is STILL REAL.**
  Neither a same-module nor a cross-module call to `Machine.start_link(0)`
  resolves: the `fsm` submodule is folded into its enclosing module and no
  callable generated module is emitted. The diagnostic has improved from the
  old opaque `missing_module` to `E091 UNKNOWN MODULE` / `UNKNOWN VALUE`, but
  the capability is still absent. The FSM_GUIDE runtime example
  (`Machine.start_link(0)`) therefore does not compile.
- **limitation 3 (`Std.Otp.spawn` outside a managed declaration) is STILL
  REAL, by design** — it is a deliberate dependent-runtime capability boundary
  ("this asynchronous operation has no dependent-runtime lowering"), not a bug.
- **limitation 4 (`@extern` `String`/charlist mismatch) is STILL REAL** — it is
  the FFI contract, documented in `docs/FFI.md`.

So the docs must be corrected to say limitation 2 is fixed while 1/3/4 remain;
they must **not** be deleted wholesale. See §4.6.

### 2.2 ✅ FIXED — Holes block code generation

The old audit: "A reachable, unfilled hole compiles and runs silently."

**Re-verified now:**

```
$ cure compile hole.cure   → CODE GENERATION FAILED [E101] ... unfilled_hole ... (exit 1)
$ cure run hole.cure       → UNFILLED HOLE [E014] "The definition `f` still contains an unfinished hole." (exit 1)
$ cure compile lib/        → CODE GENERATION FAILED [E101] ... unfilled_hole ... (exit 1)
```

The gate is `Emit.reject_holes/2` (`lib/cure/elab/emit.ex`), called from both real
codegen entry points, validating the pre-erase body against
`Validator.release_config()` (`:no_hole => :reject`). The old "proof search silently
fills the hole" regression is pinned by `test/cure/elab/hole_firewall_test.exs`.

**Residual gap (Medium, see §4.2):** `cure check hole.cure` still prints `OK` and
exits 0 with no warning that `cure compile` will later fail. `Program.hole_goals/1`
exists to report hole goals but is not called by `check`.

**Resolved (see §4.2):** `cure check` now reports each hole goal as an E014 warning
and `--strict` makes it a non-zero exit; the dead `Program.check_codegen_ready/1`
duplicate was removed so `Emit.reject_holes/2` is the single enforcement point.

### 2.3 ✅ FIXED — `@total true` is enforced

The old audit: `@total true` was a documented no-op.

**Re-verified now:**

```
$ cure check total.cure    # fn down(n: Nat) recurses on a LARGER argument
-- FUNCTION IS NOT TOTAL [E013] ------------------------------------- total.cure
`Tot#down` is marked `@total true`, so the compiler must prove that every call
to it terminates, but it cannot.
Hint: Make each recursive call use a structurally smaller argument, or remove the `@total true` annotation
```

`Declarations` records the obligation; the pipeline rejects the module unless the
kernel certifies totality. `@total false` is an explicit opt-out.

### 2.4 ✅ FIXED — Stdlib `Option`/`Result` encoding contradiction

The old audit found `core.cure` documenting `{:some, v}`/`{:none}` while
`option.cure` said `{:Some, v}`/`:None`. Both now agree on the OTP-conventional
`{:some, v}` / `:none` (lowercase). See `lib/std/option.cure:7-8,38-42` and
`lib/std/core.cure:6,180-187`.

### 2.5 ✅ LARGELY FIXED — God files / error swallowing / debug output

- `IO.inspect`/`dbg`: **81 → 3**.
- `rescue` sites: **398 → 123**.
- The diagnostic adapter has been **decomposed** into 14 sub-modules
  (`lib/cure/diagnostic/adapter/{type,name,macro,pattern,proof,...}.ex`).
- `lib/cure/elab/` is now **39 modules** (was a handful of monoliths).

**But see §4.1** — `elaborator.ex` (16,249 LOC, 1,125 defs), `parser.ex` (15,305 LOC,
896 defs), and `adapter.ex` (6,932 LOC, 1,117 defs) remain single-`defmodule` god files.

### 2.6 ✅ FIXED — CLI exit codes

The old audit's iteration-14/15 CLI findings (unknown command exits 0; `stdlib`
exits 0 on failure; fixed-arity commands misblame "Unknown command") are resolved.
**Re-verified:** `typo`, `deps badcmd`, `compile` (no args), `fmt <missing>` all
exit **1**; `check <ok>`, `version` exit **0**.

### 4.2 ✅ FIXED — `cure check` now surfaces holes

**Was:** `cure check hole.cure` → `hole.cure: OK` (exit 0), while `cure compile`
failed. `Program.hole_goals/1` (`program.ex:2210`) existed precisely to report hole
goals and was used by the REPL (`repl.ex:581`) but **not by `check`**. A user who
checked a file with a hole got a false green. Relatedly,
`Program.check_codegen_ready/1` (`program.ex:2229`) was **dead in production** — its
only callers were tests; the live gate is `Emit.reject_holes/2`. Two implementations
of one invariant was a drift risk.

**Now:**

- `cmd_check` (`cli.ex`) calls `Program.hole_goals/1` on the checked environment and
  emits an **E014 warning** for every hole goal (definition, goal type, local
  context). A hole is a development state, not an error, so the exit stays **0** by
  default and the message reads `OK (with N unfilled hole(s))`; **`--strict`**
  promotes it to a non-zero exit for CI. `check` and `compile` now agree.
- `Program.check_codegen_ready/1` is **deleted**. The single enforcement point is
  `Emit.reject_holes/2`, reached through the public `Emit.compile_forms/2` entry —
  the same gate production uses. The tests that exercised the dead duplicate were
  migrated to `Emit.compile_forms/2`, so the invariant is now pinned where it is
  actually enforced.

### 4.3 ✅ FIXED — LSP tooling surface

**Was:**

- **Unsound rename.** `server.ex:1561-1597` renamed by `\bword\b` regex across every
  line — **it renamed the symbol inside comments and string literals**. It was not
  scope-aware.
- **Missing features.** No `textDocument/references`, `documentHighlight`,
  `foldingRange`, `completionItem/resolve`, `rangeFormatting`, `onTypeFormatting`,
  `callHierarchy/*`. "Find references" was the most conspicuous gap for a language
  with a module resolver.
- **Semantic tokens over-declared.** The legend declared 8 token types but the
  scanner only ever emitted type 0 (keyword); functions/types/strings/numbers/comments
  got no semantic highlighting.
- **Silent request drops.** The catch-all `do_handle(_method,...)` returned no response
  for an unsupported method with an `id`, so the client hung instead of receiving a
  `MethodNotFound` error (verified with `textDocument/references`).
- **Diagnostics may diverge from `cure check`** — `compute_diagnostics` called only
  `Elab.Program.elaborate/2`, not the full compiler pipeline.
- **Code-lens command was a no-op** (`"cure.type.<n>"` is not a registered command).

**Now:**

- **Rename is scope-aware.** `compute_rename/5` masks comments and string/char
  literals (position-preserving) before matching, so a rename never rewrites the
  symbol inside a comment or a string. `compute_references/6` and
  `compute_document_highlights/3` share the same masking.
- **New request handlers**, all advertised in `initialize`:
  `textDocument/references`, `textDocument/documentHighlight`,
  `textDocument/foldingRange`, `textDocument/rangeFormatting`,
  `textDocument/onTypeFormatting`, and the full `callHierarchy/*` family
  (`prepareCallHierarchy`, `incomingCalls`, `outgoingCalls`).
- **Semantic tokens emit the declared types.** The scanner now classifies
  keywords, function names, type names, string literals, numbers, comments and
  operators — not just keywords — so the 8-type legend is honest.
- **No silent request drops.** The catch-all answers any request carrying an `id`
  with JSON-RPC `MethodNotFound` (`-32601`); notifications (no `id`) stay silent,
  per JSON-RPC 2.0. `Transport.send_error/3` is the new error-response primitive.
- **Diagnostics match `cure check`.** `compute_diagnostics/3` now runs the same
  `Cure.Compiler.check_source/2` front-end pipeline `cure check` uses (lex, parse,
  declaration-use expansion, lifted-module validation, elaboration, totality), so
  the editor and the command line agree.
- **Code lens is self-describing.** The lens title carries the function's
  signature (the type/effect summary) and no longer references the unregistered
  `cure.type.<n>` command; a `data` payload is available for `codeLens/resolve`.

### 4.4 ✅ FIXED — Quality gates are now enforced

**Was:**

- **Dialyzer was disabled in CI** (`ci.yml:88-92` commented out) despite `mix.exs`
  configuring it fully, `.dialyzer/ignore.exs` maintaining a curated baseline, and
  the README documenting `mix dialyzer` as a quality gate. The PLT cache steps still
  ran, wasting CI time on an artifact never used.
- **No coverage threshold anywhere.** No `minimum_coverage`, no `.coveralls.yml`, no
  `mix coveralls` CI step — coverage could regress to 0% silently.
- **Single toolchain in CI** (Elixir 1.20 / OTP 29) despite `mix.exs` declaring
  `elixir: "~> 1.18"` — the declared floor was untested.

**Now:**

- **Dialyzer runs in CI** (Linux only, where the PLT is built and cached). The
  previously commented-out `mix dialyzer --plt` / `mix dialyzer --format github`
  steps are enabled, so the PLT cache is no longer wasted and the curated baseline
  is actually enforced.
- **Coverage is gated.** `mix.exs` sets `test_coverage: [tool: ExCoveralls,
  minimum_coverage: 78]` and CI runs `mix coveralls`, so coverage can no longer
  regress silently. Measured line coverage at introduction was **80.6%**; the
  floor sits a little below it as a ratchet (raise as coverage improves, never
  lower to make a red build green). The Antigen tests that drive the node-global
  `:cover` server directly (which would tear down ExCoveralls' session and report
  `0.0%`) are tagged `:cover_machinery` and excluded from the coverage step only;
  the normal test run still exercises them.
- **The declared floor is tested.** The CI matrix now includes an
  `elixir: "1.18" / otp: "27"` entry alongside the primary `1.20 / 29` pair, so the
  `elixir: "~> 1.18"` declaration in `mix.exs` is exercised.

**Remaining (acknowledged debt):** `.dialyzer/ignore.exs` still suppresses warnings,
including in the soundness-critical kernel (`kernel.ex: :call, :no_return`;
`inductive.ex: :call, :call_with_opaque, :invalid_contract, :pattern_match_cov`).
The file itself flags this as debt ("Adding to it is a debt, not a fix"); the
suppressions are now *enforced* (CI fails on a new, unsuppressed warning) rather
than merely documented. (Deferred — see §4.1 maintainer note.)

### 4.5 ✅ Test-suite ambiguities (false-green risk)

**Fixed and verified (this pass).** Each ambiguity now has one unambiguous
contract; the vacuous passes are gone from the default suite and the stale
naming/comments are corrected.

- **`:atomvm` tests no longer pass vacuously.** `test/cure/compiler/atomvm_container_test.exs`
  and `atomvm_regex_container_test.exs` guard every assertion behind
  `File.exists?(atomvm)` with a hard-coded macOS path
  (`/Users/ch/Develop/esp32-beam/AtomVM`). CI installs no AtomVM, so the old
  `else assert true` branch made them green while testing nothing. **Now:** the
  `:atomvm` tag is excluded by default in `test_helper.exs` (alongside `:slow`),
  so these tests do not run — and therefore cannot vacuously pass — in the
  default suite or in CI. When a developer *explicitly* requests them with
  `mix test --include atomvm`, a missing AtomVM now **fails loudly** (`flunk`
  naming the three required paths and `ATOMVM_ROOT`) instead of silently passing.
- **`:canonical_module_pipeline_red` naming retired.** The three `_red` files
  (~900 LOC) were not excluded and ran in the default suite, while
  `scripts/check-canonical-module-pipeline` read as if they should be held out —
  an ambiguous green/red contract. The build-to-green pin **landed** (commit
  `36b1dee2`, "Complete the canonical module pipeline"), so the `_red` suffix and
  the `:canonical_module_pipeline_red` tag were **stale**. **Now:** the files are
  renamed to `canonical_module_pipeline_{contract,full,boundary}_test.exs`, the
  modules drop the `Red` suffix, and the tag is `:canonical_module_pipeline`
  (a grouping tag only — the tests are ordinary green tests in the default
  suite). `scripts/check-canonical-module-pipeline` is documented for what it is:
  a focused convenience loop, not a gate or an exclusion list.
- **Stale "genuinely red" comment corrected.** The comment on
  `type_directed_overload_test.exs:27-34` claimed the feature was "genuinely
  red" and told the reader to "delete the `@tag :skip`" — but no `@tag :skip`
  existed and the feature had landed. **Now:** the comment states the feature is
  **LANDED** and that the module is green in the default suite.
- **`:examples` tests now run in CI.** They are excluded by default
  (`ExUnit.configure(exclude: [examples: true])`) and CI passed only
  `--include slow`, so the two `examples/hello.cure` CLI smoke tests never ran.
  **Now:** CI runs `mix test --include slow --include examples`.
- **`:t3` exclusion claim: none exists, and none was added.** There is no `:t3`
  tag or exclusion anywhere in the tree — the claim was fictional. No code change
  is needed; the default-exclude set in `test_helper.exs` is now exactly
  `[:slow, :atomvm]`, both documented, and no fictional entry was introduced.

  block from `Commands.help_lines/0`, the unknown-command suggestion uses
  `Commands.names/0`, and the `@moduledoc` points at the registry instead of
  duplicating a partial list. The registry names were cross-checked against the
  dispatch `case` and match exactly. A new `docs/README.md` index was added.

### 4.7 🟡 Stdlib consistency debt

- **Naming: three names for one operation.** `unwrap` (`core.cure:202`,
  `option.cure:57`, `result.cure:78`), `unwrap_ok` (`core.cure:123`, `match.cure:92`,
  `result.cure:71`), `unwrap_some` (`option.cure:64`, `match.cure:99`) — plus
  `unwrap_error`. The functions are duplicated across `core`/`option`/`result`/`match`.
- **`Std.Regex` lives in `lib/std_deps/regex/`, not `lib/std/`** — an inconsistent
  packaging location (13,428 LOC outside the stdlib tree).
- **Duplicate `@extern` declarations** (intentional per the binding rule, but a
  readability hazard): `:erlang, :element, 2` appears **13 times** in `otp_raw.cure`;
  `:string, :split, 3` twice in `string.cure`; `:erlang, :system_info, 1` twice in
  `system.cure`.
- **Decorator placement is inconsistent** — `@group` is at line 1 in some files and
  line 3–6 in others (comment header present or not); first `@extern` ranges from
  line 8 to line 632. No enforced file-header convention.

### 4.8 🟡 Performance: the cold build is still slow (the bottleneck moved)

From `docs/COMPILER_PERFORMANCE_BASELINES.md`:

- `Std.Actor` is **no longer** the bottleneck — it dropped from ~36 s to ~4.8 s after
  the 2026-08-10 `CharacterLiteral` fix.
- The current dominant cold cost is **`Std.Regex.Proof`** (dependent proof
  elaboration): ~82–105 s of a ~113–170 s cold total; individual declarations reach
  **25–29 s** (`thompson_alternate_acceptance_captures`).
- Warm builds are healthy (~5 s, `rebuilt=0`).

The doc is exemplary in its honesty (it refuses to claim speedups by subtracting
non-isolated samples). The actionable point: **dependent proof elaboration is the
cold-build bottleneck**, and a precompiled stdlib artifact (the `priv/ebin` path
exists) would turn a multi-minute first run into seconds.

### 4.9 🟡 `cure run` treats "nothing to run" as success

Verified: a file with no `main/0` prints *"compiled (no main/0 function)"* and
**exits 0**. `cmd_run` also ignores `main/0`'s return value unless it is non-`:ok`/
non-`nil` and never treats a returned error tuple as failure.

### 4.10 🟡 Bus factor = 1

`mix.exs` lists a single maintainer (`Aleksei Matiushkin`); the docs list a single
author. There is **no `CONTRIBUTING.md`, no `CODE_OF_CONDUCT.md`, no `SECURITY.md`,
and no user-facing docs index** (`docs/README.md`). For a 164k-LOC compiler with a
soundness-critical kernel and a "the compiler proves things" pitch, this is a
significant project risk — and the project is otherwise *ready* for contributors.

### 4.11 ✅ Minor

**Fixed and verified (this pass)** except the last item, which is external tooling
debt that cannot be fixed in this repository.

- **Unbounded `String.to_atom` removed** in `lib/cure/core/term.ex` (`from_external`
  deserializer). The `atom_lit` decode now goes through the same bounded-interning
  `sym_atom/1` helper as every other symbol (existing atoms only), so untrusted
  JSON can no longer mint permanent atoms and exhaust the atom table (K12 §D).
  A real term's atom literal was interned when its source was parsed, so valid
  terms still round-trip; pinned by a new test in `test/cure/core/term_test.exs`.
- **`System.halt(1)` → `exit({:shutdown, 1})`** in `cli.ex` (`cure migrate`'s
  error path). It was the lone `System.halt/1` in the module; every other
  non-zero exit uses the graceful form, so output flushes and shutdown hooks run.
- **E101 hole diagnostic fixed.** A hole that survives to the canonical emission
  boundary arrives as `{:beam_emission_failed, module, {:unfilled_hole, _}}` — a
  shape the codegen adapter did not route, so it fell through to the generic
  "Code generation failed" E101 with the note "This is an internal compiler
  failure; report it with the diagnostic fingerprint". A user who simply left a
  hole was told to file a compiler bug. It now routes to the user-facing **E014
  "Unfilled hole"** (source span, caret, hint) like the direct-codegen path.
  Verified end to end: `cure compile hole.cure` prints `-- UNFILLED HOLE [E014]`,
  not `CODE GENERATION FAILED [E101]`. Pinned by a new test in
  `test/cure/compiler/hole_diagnostic_test.exs`.
- **`cmd_keys_generate` unreachable code removed.** The `raise` in the `other ->`
  branch never returns, so the trailing `exit({:shutdown, 1})` was dead; the
  `rescue` below already turns the raise into the user-facing internal-exception
  diagnostic and the single exit.
- **`cmd_watch` no longer `String.to_atom/1`s `--action`.** The value is validated
  against `compile | check | test` at the CLI boundary; anything else is an
  `E099` usage error, instead of minting an atom from untrusted input and letting
  `Cure.Watch` report an unknown action from deep inside the watcher. Pinned by a
  new test in `test/cure/cli_test.exs`.
- **Ragex tooling debt (meta) — NOT fixable here.** `find_dead_code` crashes with
  `FunctionClauseError` in `Ragex.MCP.Handlers.Tools.extract_function_parts/1`,
  `find_duplicates` crashes in `MetaCredo.Analysis.Duplication.Fingerprint.normalize_ast/1`,
  and `analyze_quality` returns only `%{warnings: []}` with no per-function metrics
  (reproduced on this tree). These are bugs in the external Ragex/MetaCredo
  analysis engine, not in the Cure source, so they cannot be fixed by editing
  this repository. Recorded here as acknowledged external tooling debt: dead-code
  and duplication remain unmeasurable via Ragex until the engine is fixed.

1. **Lean into "verified concurrency".** The combination of dependent types + typed

## 6. Verdict

Cure has **materially improved** since the last audit, and in exactly the right way.
The three "correctness-of-claims" defects that were most damaging — holes that didn't
block codegen, `@total true` that did nothing, and macro containers that couldn't be
type-checked — are **all fixed and re-verified empirically**. The kernel, already the
strongest part of the project, is now backed by a **machine-checked Agda soundness and
confluence proof** and a written argument that is honest about its assumptions. The
test suite is green (6,657 / 0) and the verification infrastructure (Antigen, the Idris
oracle, the proof workflow) is research-grade.

What remains is of two kinds. The **engineering-debt** kind — god files, LSP
roughness, stdlib naming, doc drift — is normal for a project this size and is
tractable; §5.1–5.4 are a well-scoped release or two of hardening. The **process** kind
is more subtle: the quality gates (Dialyzer, coverage) are configured but not enforced,
several tests can pass vacuously, and a flagship example's README still documents bugs
that are fixed. In a language whose value proposition is *"the compiler proves
things,"* the gap between what is *configured* and what is *enforced* is the thing to
close next.

The good news is unchanged from the last audit, only more so: every gap is fixable,
the fixes are well-scoped, and the underlying machinery — including, now, a real proof
— already exists. Cure is close to being a genuinely trustworthy dependently-typed
language for the BEAM.
