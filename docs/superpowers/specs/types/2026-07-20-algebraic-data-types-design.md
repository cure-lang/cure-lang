# Cure Algebraic Data Types

**Status:** design specification.

This document consolidates Cure's algebraic-data-type model: ordinary ADTs,
parameterized families, records, indexed/GADT families, anonymous sums, empty
types, pattern matching, and runtime representation. It is intended to be the
stable language-level reference for the existing inductive kernel rather than a
new kernel feature by itself.

## 1. Design goals

Cure algebraic data types must provide:

- nominal, type-safe constructors;
- parameterized and recursive data;
- indexed families and GADT-style constructor refinement;
- exhaustive and redundancy-aware pattern matching;
- dependent indices usable in proofs and refinements;
- predictable BEAM and AtomVM representations;
- no unchecked casts or representation-dependent subtyping;
- compatibility with effectful branch bodies while keeping scrutinees and
  indices value-level;
- a path for compiler-generated anonymous sums without polluting namespaces.

The kernel remains a small inductive calculus. Surface conveniences elaborate to
ordinary families, constructors, applications, and `case` terms.

## 2. Ordinary algebraic data types

A named ADT introduces one nominal family and one constructor per alternative:

```cure
type Result(A, E) =
  Ok(A)
  | Error(E)

type Tree(A) =
  Leaf(A)
  | Branch(Tree(A), Tree(A))
```

Constructors are functions whose result is the declaring family:

```text
Ok   : {A : Type} -> A -> Result(A, E)
Error: {A : Type} -> E -> Result(A, E)
```

The family is nominal. Two declarations with the same constructor shape are
different types unless connected by an explicit type alias.

Constructor names are resolved through the normal module and import rules.
Qualified names are always available when a bare constructor is ambiguous.

An empty declaration is an empty type:

```cure
type Never =
```

No value can inhabit `Never`; elimination from it is permitted only through the
ordinary empty-case/absurd elimination path checked by the kernel.

## 3. Parameters and indices

Parameters describe data common to every constructor. Indices describe the
particular result produced by a constructor.

```cure
type Vector(A, n: Nat) indices (n) =
  Nil  : Vector(A, 0)
  Cons : A -> Vector(A, n) -> Vector(A, S(n))
```

The surface spelling may use the repository's existing `indexed type` grammar;
the semantic distinction is fixed:

```text
family parameters: uniform across constructors
family indices:    may differ per constructor
```

Indices may be arbitrary well-typed terms, including constructor applications,
type-level functions, literals, and reducible expressions. They are not runtime
proofs; they are part of the family identity and branch refinement.

## 4. GADT-style constructors

A constructor may constrain an index by choosing a specific result:

```cure
type Expr(A) indices (A) =
  EInt  : Int  -> Expr(Int)
  EBool : Bool -> Expr(Bool)
  EPair : Expr(A) -> Expr(B) -> Expr(%[A, B])
```

Matching refines the branch context. In the `EInt` branch, a scrutinee
`Expr(A)` provides evidence that `A` converts to `Int`; expressions whose types
mention `A` are checked in the refined branch context.

The refinement is generated by the dependent `case` motive and constructor
result indices. It is not implemented as a cast or a mutable type-variable
assignment.

Invalid branch bodies are rejected even when a branch is unreachable at runtime.
Vacuous branches are discharged only through a kernel-checked empty or indexed
obligation.

## 5. Records

Records are nominal single-constructor ADTs with named fields:

```cure
type User =
  User(
    id: UserId,
    name: String,
    email: String
  )
```

Construction is named and checked:

```cure
User(id: id, name: name, email: email)
```

The compiler lowers a record literal to the positional constructor in the
declaration's field order. Missing fields, extra fields, and duplicate fields
are errors. Defaults, where supported, are elaborator conveniences and do not
change the constructor's nominal type.

Field projection is resolved against the constructor declaration, not by
inspecting the runtime tuple. Record update reconstructs the constructor and
therefore preserves ordinary constructor typing and erasure.

Records with one constructor still participate in pattern matching and indexed
refinement like every other ADT.

## 6. Type aliases and opaque types

A `typealias` introduces no new family or constructors:

```cure
typealias UserId = Int
```

Conversion unfolds aliases according to the normal definitional-equality rules.

An `opaque type` introduces a nominal boundary. Its representation and
constructors are visible only in the defining module. Public functions may
construct, inspect, or convert it according to their signatures, but clients
cannot pattern-match on hidden constructors.

Aliases must not be used to bypass an opaque boundary or to create structural
equivalence between unrelated families.

## 7. Anonymous sums

Type-expression sums provide a namespace-free discriminated union:

```cure
fn parse(input: String) -> Int | String = ...
```

`A | B` elaborates to a compiler-generated nominal family with tagged
constructors. It is not value-level subtyping and does not rely on runtime type
tests over erased values.

Canonicalization must:

1. flatten nested sums;
2. unfold aliases;
3. normalize closed member types;
4. distinguish members by resolved family identity and literal type;
5. deduplicate equal members;
6. sort members deterministically;
7. collapse a one-member sum to that member.

Anonymous sums must preserve a stable generated identity across modules and
compilation runs. Members that erase to indistinguishable BEAM values use an
explicit tag representation; transparent untagged unions are not part of this
design.

## 8. Constructors and implicit parameters

Type parameters and inferred indices may be erased when their quantity is zero,
but their types remain part of constructor checking. A constructor application
must:

- insert inferred parameters only at declared implicit positions;
- solve them from explicit arguments, expected result types, and indexed
  constraints;
- reject unresolved metavariables at the definition boundary;
- preserve relevant implicit arguments when erasure or branch refinement needs
  them;
- reject wrong-family, wrong-index, and wrong-arity applications.

An explicit annotation or expected type may guide constructor elaboration, but it
may not introduce a cast.

## 9. Pattern matching

Pattern matching is the eliminator for ADTs:

```cure
fn size(tree: Tree(A)) -> Nat =
  match tree
    Leaf(_) -> 1
    Branch(left, right) -> size(left) + size(right)
```

The compiler checks:

- constructor validity and family identity;
- pattern arity and field types;
- index refinement in each branch;
- exhaustiveness;
- unreachable or redundant arms where the analysis can prove them;
- branch result compatibility.

A match scrutinee must be a value unless the enclosing computation syntax first
binds the result of an effectful computation. Effects belong to branch bodies or
the surrounding computation judgment, never to the scrutinee's type.

Pattern coverage is a static safety check. It must not be replaced by a runtime
catch-all that fabricates a value of the declared result type.

## 10. Dependent elimination

For an indexed family, the elaborator constructs a motive over the scrutinee's
indices and checks every branch against the motive applied to that constructor's
result indices.

The kernel is responsible for:

- checking the motive;
- checking constructor branch arity;
- applying the motive to constructor indices;
- refining context entries whose types mention the scrutinee indices;
- checking branch terms under the refined context;
- preserving termination and conversion guarantees.

The elaborator may perform name resolution, pattern desugaring, and expected-type
driving, but it must emit an ordinary Core `case` that the kernel can re-check.

## 11. Recursion and positivity

Recursive families and constructors must satisfy strict positivity. A recursive
occurrence is permitted in covariant constructor fields, including nested
parameterized positions approved by the positivity checker.

Negative occurrences are rejected:

```cure
type Bad = Bad -> Int
```

Mutual recursive families must be checked as a group. The positivity and
termination checks operate on the fully resolved declaration graph, not merely
on textual declaration order.

General recursive functions remain subject to totality checking. Productive
runtime loops may be computations under the algebraic-effects design, but they
must not enter kernel normalization as terminating values.

## 12. Runtime representation

The default erasure is constructor-directed:

- nullary constructors become atoms;
- constructors with present fields become tagged tuples;
- erased parameters and proofs do not appear at runtime;
- records use the same constructor representation as their underlying ADT;
- indexed arguments are erased unless marked relevant by the type/usage rules.

Builtin families may opt into validated native representations:

```text
Bool -> BEAM booleans/atoms
Nat  -> machine or arbitrary-precision integers
List -> native BEAM lists where the representation contract permits it
```

Such representations require a trusted, schema-validated builtin binding and
must preserve constructor identity, pattern matching, conversion, and foreign
boundary behavior. A structurally similar user family does not automatically
receive a builtin representation.

AtomVM and Unix BEAM code generation must agree on the observable value shape.

## 13. Effects and ADTs

ADT values are ordinary values and may occur in types, proofs, refinements, and
normalization when they are pure and total. Computations producing ADT values
are separate:

```cure
fn receive_message() -> Message ! Otp.Receive
```

The result type is `Message`, not `Effect(Message)`. A caller sequences the
computation, then pattern-matches the resulting value.

Handlers and actor macros may generate ADTs for commands, transitions, replies,
and protocol states. Generated families must be elaborated and kernel-checked
like user-written families.

## 14. Equality, proofs, and refinements

Constructor equality is nominal and follows definitional equality. No two
distinct constructors are equal merely because their erased BEAM terms happen
to coincide.

Equality witnesses, index proofs, coverage certificates, and refinement proofs
are ordinary proof-relevant values subject to the pure logical fragment. An
effectful operation cannot construct a proof merely by returning a value with a
matching runtime representation.

Foreign functions cannot fabricate ADT constructors in proof-relevant or
refinement positions without an explicit audited evidence contract.

## 15. Modules, visibility, and derivation

A family may expose:

- its type name;
- selected constructors;
- record fields and projections;
- derived functions or interfaces.

Private constructors enforce abstraction while preserving the family's nominal
identity. Deriving mechanisms generate ordinary functions, declarations, or
macros; they do not add trusted kernel constructors without schema validation.

Generated declarations must retain source spans, module ownership, and stable
names for diagnostics and incremental compilation.

## 16. Required compiler operations

The implementation must provide or preserve operations equivalent to:

```text
register_family(declaration)
register_constructor(family, constructor)
check_positivity(family_group)
infer_constructor_application(context, constructor, arguments)
check_constructor_application(context, constructor, arguments, expected)
build_indexed_motive(scrutinee, family, result_type)
check_case(context, scrutinee, motive, branches)
check_coverage(family, patterns)
canonicalize_anonymous_sum(members)
erase_constructor_application(term, representation)
```

The kernel must reject malformed families, constructors, cases, and serialized
signatures rather than relying on elaborator invariants alone.

## 17. Implementation boundaries

Surface syntax, constructor resolution, record conveniences, anonymous-sum
canonicalization, and diagnostics belong primarily to the parser/elaborator.

Family formation, positivity, constructor typing, indexed conversion, case
checking, certificates, serialization validation, and final-core validation
belong to the trusted core boundary and require the project's full TCB and
Antigen gates when changed.

Runtime representation selection and BEAM/AtomVM lowering belong to erasure and
code generation, with cross-target representation tests.

## 18. Non-goals

This specification does not introduce:

- structural subtyping between unrelated ADTs;
- untagged TypeScript-style unions;
- unchecked casts or `believe_me`-style escape hatches;
- row-polymorphic variants;
- automatic representation equality between distinct families;
- effectful type-level computation;
- unrestricted general recursion in the kernel;
- a requirement that every ADT have a native runtime representation.

## 19. Acceptance criteria

The ADT system is complete when:

1. Ordinary, recursive, parameterized, record, empty, and indexed families are
   represented uniformly in Core.
2. Constructors are nominally resolved and checked.
3. GADT branches refine dependent indices soundly.
4. Pattern matching is exhaustive and branch result types are checked.
5. Positivity and mutual-recursion checks reject invalid families.
6. Anonymous sums have deterministic canonical identities and tagged erasure.
7. Aliases and opaque boundaries behave distinctly.
8. Erasure removes only approved irrelevant parameters and proofs.
9. Unix BEAM and AtomVM agree on observable representations.
10. Effects remain outside value typing, proof construction, and normalization.
11. Foreign and generated declarations cannot bypass family or proof checks.
12. Malformed Core and serialized signatures are rejected by the trusted gates.
