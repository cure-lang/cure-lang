## §1 Locked design decisions

1. **Builtin-op def-kind, registry-keyed (kills risk R1).** Ops are seeded as BODY-LESS defs carrying a `builtin_op` marker in the def record (mechanism analogous to `Inductive.register_builtin`, inductive.ex:119-137), registered under stable keys. EVERY consumer — the Normalise compute hook, emit's inline, GuardLint's Z3 translation — resolves through the def record/registry, NEVER bare global names. Rationale: `qualified_syms` is `:off` and cross-module global collision is a known gap (the standing "global def collision gap" — `Env.defs` has no rebind protection); a user def named `int_add` (the actual reserved key — see decision 3's monomorphic naming; a plain `add` is never a registered key under this design, so it is not itself an adversarial example) must not be delta-computed (kernel unsoundness), Z3-translated (lint unsoundness), or operator-inlined (miscompile). Emit's existing `connective_inline` (emit.ex:216-244) keys on bare atoms — a pre-existing smell for canonical prelude names (`and`/`or`/`not`/`eq`/`ne`, which ARE plausible user-chosen names, unlike `int_add`); NOT copied, NOT fixed here (noted for follow-up).
2. **Compute hook in the certified-δ engine.** `unfold_certified_head` (normalise.ex:196-244) gains a builtin-op branch, checked BEFORE the existing certified-body path in the same `{:nglobal, name}` case arm: head is a builtin-op def AND every spine arg whnfs to a literal value → compute via the EXISTING audited fold table (`Eval.fold`, eval.ex:102-142, extracted to a shared home so Eval and Normalise call one table); otherwise stay stuck (§G.1 rule 1 preserved verbatim — div/rem by literal zero remains neutral). The ordering is load-bearing, not stylistic: `Term.closed?/1`'s leaf catch-all (term.ex:137) treats a bare `nil` as vacuously closed, so IF a builtin-op def were seeded with `body: nil` and the NEW branch did not intercept first, the OLD generic path's `with true <- Env.certified?(sig, name), %{body: body} <- Env.get_def(sig, name), true <- Term.closed?(body) do ... Eval.eval(body, []) ...` would pass its guards on a builtin-op def and then call `Eval.eval(nil, [])` — which has no clause for a bare `nil` term and crashes. So: the builtin-op branch is a genuinely SEPARATE dispatch keyed on the `builtin_op` marker (via `Env.get_def`), checked first; it does not rely on `Env.certified?` at all for its own gating. Whether `Env.certified?` ALSO happens to answer true for these names (e.g. because seeding additionally calls `Env.certify/2`, which is harmless here only because of the nil-vacuously-closed quirk above) is incidental, not load-bearing, and must not be the mechanism a reader relies on for safety. Builtin-op defs have no self-calls and no termination question (size-change treats them as terminal) — this is risk **R4** (certificate/termination interplay for a bodyless def-kind), closed by the ordering argument above, not by `Env.certified?` alone. `Conv`'s lazy-δ inherits the hook through the same engine (`Normalise.whnf_value` takes a bare `Env.t()`, conv.ex:56-65 — no `Context.t()` needed); `same_neutral_no_delta?` loop-safety is trivial (no body to loop on).
3. **Monomorphic per-type op globals (Lean-aligned).** `infer_prim`'s ad-hoc polymorphism (add/sub/mul/div numeric-polymorphic, eq/ne any-shared-type) is NOT reproduced. The seeded set is monomorphic pairs, exactly the ops with live producers: `int_add/int_sub/int_mul/int_div/int_rem/int_lt/int_le/int_gt/int_ge/int_eq/int_ne : Int -> Int -> {Int|Bool}` and `float_add/float_sub/float_mul/float_div/float_lt/float_le/float_gt/float_ge/float_eq/float_ne : Float -> Float -> {Float|Bool}` plus `int_neg/float_neg` (unary; `neg` is produced only by core_bridge today). The ELABORATOR type-directs the choice: it already type-directs `==` via `bool_operand?`/`primitive_scrut_kind` (`build_binop`'s `:==`/`:!=` clauses at elaborator.ex:638-648, `bool_operand?` at :665, `primitive_scrut_kind`'s actual int/float/bool classifier at elaborator.ex:2601-2608 — note the general arithmetic clause, `build_binop(op_sym, l, r, _l_type, _sig)` at :650-655, currently discards `l_type`; `l_type` IS already threaded as a parameter into every `build_binop` clause, it is simply unused by the catch-all today, so wiring `primitive_scrut_kind(l_type, sig)` into that one clause is the whole change). Bool operands keep routing to the Std.Bool case-defs (unchanged); Int → `int_*`; Float → `float_*`; underdetermined/other operand types → elaboration error naming the operator (today's prim would have been typed-then-stuck anyway; the honest surface is a type-directed reject — any surface program this newly rejects is a STOP-and-report for adjudication, expected count ZERO since eq/ne on non-numerics never folds today — confirmed: `Eval.fold` (eval.ex:100-141) has `:eq`/`:ne` clauses only for `{:vint,_}`/`{:vfloat,_}` pairs, nothing for `{:vctor,...}` — and no oracle fixture exercises it — confirmed by sampling: `test/oracle/**/*.cure` contains exactly 4 files using `==`, all of the form `x when x == <int literal>` in guard position; the plan must still re-verify this count before flipping, since this is a sample not an exhaustive audit). Zombie `and/or/not` prims are NOT seeded (kernel already rejects them; core_bridge stops producing them — its Bool folding already lives surface-side in `fold_bool_binop`, reduce.ex precedent).
4. **The types-pipeline carve-out is pre-authorized NOW (D2 §8 precedent, not re-litigated mid-run):** `lib/cure/types/core_bridge.ex` (to_core prim producers :54-70, from_core inverses :143-147) and `lib/cure/types/reduce.ex` are Core-grammar CONSUMERS. `to_core` produces builtin-op global spines (registry-consistent atoms) — `to_core` is UNTYPED (surface AST → Core, no Env/Context), so unlike the elaborator it cannot consult a type value to pick `int_*` vs `float_*`; it must decide from the SHAPE of its own already-converted operand sub-terms instead: either recursively-converted operand being `{:float_lit,_}` selects `float_*`, otherwise `int_*` (this is exactly the case space `core_bridge_test.exs` exercises today — `"float arithmetic folds through the kernel"` uses two float literals, never a mix of a literal and a free `{:variable,…}`/`{:global,…}` operand). A free (unbound) operand of unknown eventual type therefore defaults to `int_*`, matching the practical convention that dependent-type indices — Cure's only live use of this bridge — are Nat/Int-valued; this default is unverified for a hypothetical float-valued free index variable, so the plan's corpus survey (decision 3) must also confirm zero live float-typed dependent-index arithmetic before relying on it. `from_core` reads them back — NOT automatically: `from_core`'s own reverse clauses (currently `from_core({:prim, :neg, [x]})`, `from_core({:prim, :not, [x]})`, and `from_core({:prim, op, [l, r]})` matching via `@from_binop`, core_bridge.ex:143-147) must gain DEDICATED replacements recognizing a builtin-op-headed spine (`{:app, {:app, {:global, :int_add}, l}, r}` etc.) and re-spelling it back to `{:binary_op, [operator: :+], [l, r]}` via the monomorphic-name-to-surface-operator reverse map — checked BEFORE `from_core`'s existing generic `{:app, _f, _x} = app` clause (which unwinds any `{:global, name}`-headed spine into a `{:function_call, [name: ...], args}`), since that generic clause would otherwise mis-render `3 + 5`'s Core form as a call to a function literally named `"int_add"` instead of a `+` binary-op AST node. This from_core retarget is symmetric to (and as load-bearing as) the to_core producer change, and §4's grammar-grep acceptance check must extend to `lib/cure/types/core_bridge.ex` (not just core/elab/antigen — see §4.5) to confirm no `{:prim,` pattern survives there either. `reduce.ex`'s `kernel_normalize_via_core` (defined :97, the `Eval.eval([])` call at :99) switches from sig-free `Eval.eval([])` to the kernel's signature-carrying normalization over a builtins-seeded env — implementable without a full `Context.t()`, since `Normalise.whnf_value/3` (normalise.ex:51-65) already accepts a bare `Env.t() | nil` directly — so classic-pipeline constant folding KEEPS working AND keeps its "no arithmetic folded outside Cure.Core" design contract (kills risk R2 the principled way — the Bool-style private-fold fallback is the rejected alternative). Behavior-pinned by `test/cure/types/reduce_test.exs`, whose assertions (e.g. `assert {:literal, _, 8} = Reduce.normalize(binop(:+, lit(3), lit(5)))`) directly exercise the arithmetic-folding path this decision touches — this is the load-bearing pin. `test/cure/types/equality_test.exs` also calls into `Reduce.equal?` (via `Cure.Types.Equality.check_refl/3` and `.rewrite/2`, which invoke `Reduce.equal?` at equality.ex:80/83/114) but its own assertions only compare literal-vs-literal or variable-vs-literal terms — none require genuine arithmetic folding — so it is only an incidental crash-level backstop for this change, not an independent behavioral pin on int/float dispatch; do not read "Equality tests green" as confirming arithmetic-folding correctness beyond what ReduceTest already covers. NOTHING ELSE under `lib/cure/types/`/`lib/cure/compiler/` changes.
5. **Emit: registry-keyed saturated inline + eta-wrapper for first-class use (kills R7).** Saturated builtin-op spines lower to the SAME BEAM operators as today (erl_binop/erl_unop tables, emit.ex:293-308; inline precedent: D2's `sigma_first/second → element/2`, emit.ex:236-241 — but keyed via the registry per decision 1, not bare atoms). ## §1-A Amendment A1 (2026-07-09, adjudicated mid-execution): structural equality globals `struct_eq`/`struct_ne`

**Trigger (verified counterexample to decision 3's zero-prediction).** The plan's Task 2 Step 0 corpus survey found live, green, BEAM-executing programs using `==` on non-int/float/bool operands: `test/cure/elab/ctor_guard_test.exs:17/18/66/100` — constructor guards `NCons(h, t) when h == Z()` with `h : Nat`. Verified elaboration path: guard → `elaborate_expr_checked` fallback → `build_binop(:==, …, l_type = Nat vdata)` → `{:prim, :eq, [l, r]}`; `infer_prim` :eq (kernel.ex:1098) types it at Bool for ANY shared type; `Eval.fold` has `:eq`/`:ne` clauses ONLY for vint/vfloat pairs (eval.ex:122-125), so ADT equality is **kernel-neutral** (never reduced at type-checking time); emit lowers it to BEAM `:==` (emit.ex:188/:298) — the comparison is runtime-structural. Note also `bool_operand?`'s own comment (elaborator.ex:661-664): a **type-variable or neutral** operand type takes the same path, so decision 3's "other → elaboration error" would additionally reject polymorphic `x == y` — the counterexample class is wider than the Nat guards.

**Adjudication (parity criterion, autonomous-parity directive).** Idris2 ACCEPTS `h == Z` (prelude `Eq Nat`); so does Lean (`BEq`/`DecidableEq` deriving). Rejecting it is a parity regression at the user-program level — option 3 (retire the test) is out. Nat→`int_eq` (option 2) is type-incorrect at elaboration (`{:vdata, :Nat}` ≠ Int) and non-general. The adopted fix is option 1 done as **globals, not a grammar node**: the current semantics survive verbatim, the `{:prim}` strip stays complete, and zero programs are newly rejected.

**Amended decision 3′ — the seeded op set is 25, not 23:** the 23 monomorphic ops PLUS two polymorphic structural ops, `struct_eq` and `struct_ne : Pi(a: Type). Pi(_: a). Pi(_: a). Bool` (explicit, ω-present type argument — no erased-implicit machinery; emit drops it). Both are registry-keyed builtin-op defs exactly like the other 23 (R1 protection identical; distinct marker atoms `:struct_eq`/`:struct_ne`). They are a **transitional Core representation of today's structural runtime equality**, NOT a new equational theory: the future Equatable/deriving surface (stdlib-dependent-expansion) will retarget exactly ONE site — `build_binop`'s fallback branch. String `==` (no live producer found) is covered generically with no special-casing.

Sub-decisions:

- **Semantics = today's `{:prim, :eq/:ne}` verbatim.** Compute hook: `struct_eq`/`struct_ne` applied to `[tyval, l, r]` delegates to `Eval.fold(:eq/:ne, [l, r])` — the type argument is not consulted. By construction this folds IFF both value args are int or float literals (covering late-instantiated polymorphic operands, same as today) and stays **neutral on everything else** — ADT applications never compute in the kernel, exactly as now. Conv compares open `struct_eq` spines by the generic global-spine congruence (same strength as the `{:nprim}` clause being stripped).
- **`build_binop` dispatch for `:==`/`:!=` becomes 4-way:** `{:ok, :bool}` → `app2(:eq/:ne)` (Std.Bool, unchanged); `{:ok, :int}` → `int_eq`/`int_ne`; `{:ok, :float}` → `float_eq`/`float_ne`; `:error` → `struct_eq`/`struct_ne` applied to the **readback (quote) of `l_type`** plus `l`, `r` — NOT an elaboration error. This needs the operand type as a Core term: thread `ctx` (or the quoted type) into `build_binop` — signature latitude to the executor; the D1 reify precedent applies. Arithmetic ops' dispatch (`+`/`-`/… → error on non-numeric) is UNCHANGED from decision 3 — `infer_prim` already requires numeric operands there, so no accepted program exists to lose (survey-confirmed: only `==`/`!=` had non-primitive uses).
- **GuardLint: `struct_eq`/`struct_ne` spines ALWAYS fall to the sound uninterpreted-atom fallback** (never-over-prove direction). Enumerated honestly: potentially weaker than today's `{:prim, :eq}` for a guard whose operands are int-valued but whose TYPE was neutral at elaboration — the corpus has none (int-typed operands now route to `int_eq`, which GuardLint does translate).
- **Emit: registry-keyed clauses** — saturated 3-arg spine → BEAM `==`/`/=` on args 2 and 3 (type argument dropped); unsaturated → curried fun wrapper per decision 5's mechanism (innermost body `L == R`). Runtime bit-identical to today's prim lowering for every existing program.
