# Nat→Int Runtime Erasure — Design

**Status:** approved design (operator standing batch authorization; the feature is Phase 2 of the operator-approved builtin-inductive foundation spec, `docs/superpowers/specs/kernel/2026-07-03-builtin-inductive-foundation-design.md` §3 / lines 215–284).
**Layer:** C (untrusted erase/emit, `lib/cure/elab/emit.ex`) + tests. **Zero changes under `lib/cure/core/`** and zero changes to `lib/cure/elab/erase.ex`'s representation behavior (Core stays inductive end-to-end; see §2.5). **Exception, scoped in §2.1:** rule 4 (first-class `S`/`Z`) additionally requires a small fix in `lib/cure/elab/elaborator.ex` (still E-layer, untrusted, not K/TCB — no gate triggered) because the gap it depends on isn't an emit-side hook at all; see §2.1's third bullet.
**Batch:** parity queue item C-3 (task #12), worktree `kernel-parity-batch`, branch `autopilot/kernel-parity-batch`.

## §0 Context — Phase 1 is landed; this is pure consumption

The foundation's Phase 1 (TCB, gated) landed in full: the `:nat` schema `[{:Z, 0}, {:S, 1}]` (`lib/cure/core/builtins.ex:16`), seeding (`builtins.ex:55-60,91-97`), the registry (`lib/cure/core/inductive.ex:125-143`, `builtins:` field), and the `@builtin(:nat)` binding on the prelude Nat (`lib/std/nat.cure:9-10`, honored by `Cure.Elab.Program.maybe_register_builtin/3`, `program.ex:738-757`, prelude-only). Test pins: `test/cure/core/builtins_seed_test.exs:22`, `builtins_schema_test.exs:44`, `no_gradual_any_test.exs:23`.

What does NOT exist is the representation change itself: today `Z()` emits the BEAM atom `:Z` and `S(n)` the tagged tuple `{:S, n}` (`lib/cure/elab/emit.ex:158-169`), so a Nat n is O(n) heap — fatal on ESP32/AtomVM, the repo's stated reason to exist. The Bool→atom special case (`emit.ex:160-161`, helpers `bool_ctor?/bool_atom/bool_atom_or_self` at `emit.ex:363-370`) is the landed structural precedent, and `builtins.ex`'s moduledoc (lines 4-9) already documents the intended `Z/S -> int` mapping. This spec is the Idris "Nat hack" (`%builtin Natural`; vendored: `reference/idris2/src/TTImp/ProcessBuiltin.idr:211-226` marks, `reference/idris2/src/Core/CompileExpr.idr:19-56` ZERO/SUCC ConInfo flags, backends lower Z→0 / S→+1 / case→zero-test-and-minus-one), realized as registry lookups at the two emit hook sites.

## §1 Goal — the four lowering rules (foundation §3, lines 215-219)

For the family registered as `Inductive.builtin(env, :nat)` — and ONLY that family (§2.4):

1. `Z()` ⇒ integer `0`; `S(e)` ⇒ `e + 1` (native BEAM `+`).
2. `case n of Z() -> a | S(k) -> b` ⇒ BEAM `case n of 0 -> a; N when N > 0 -> K = N - 1, b` (k binds the predecessor; see §2.2c).
3. Nat-typed prim/arithmetic ⇒ machine op — **vacuous in v1**: no Nat-typed `{:prim}` exists (Std.Nat arithmetic is recursive `:case` defs, `lib/std/nat.cure`); those defs compile unchanged over the Int rep (§2.6).
4. `S`/`Z` as first-class values ⇒ `0` and the increment closure `fun(X) -> X + 1 end`.

Runtime Nat becomes O(1) space. Time complexity of Std.Nat arithmetic is unchanged (O(n) recursion) — the ESP32 killer was space, and native-op inlining is a non-goal (§6).

## §2 Design

### §2.1 Hook sites — emit-layer only, mirroring Bool

Two sites in `lib/cure/elab/emit.ex`, exactly where Bool hooks today:

- `lower(env, {:ctor, name, args}, ctx)` (`emit.ex:158-169`): before the generic atom/tuple fallthrough, a `nat_ctor?` check (same shape as `bool_ctor?` at 363: `Inductive.builtin(env, :nat) == ctor_family(env, name)`) dispatches `Z/0` → integer literal `0`, `S/1` → the `+ 1` form on the lowered argument.
- `lower(env, {:case, …}, ctx)` (`emit.ex:171-173`) / `branch_clause/3` (`emit.ex:308-333`): when the scrutinee's branch constructors belong to the `:nat` family, emit the integer-clause form of rule 2 instead of atom/tuple patterns.
- Ctor-in-function-position / first-class references. **Verified: this is not an unlocated emit clause — no such clause exists today, for any positive-arity constructor, Nat included, because the term never reaches emit.** A bare identifier resolves through `resolve_free/2` (`lib/cure/elab/elaborator.ex:4745-4772`), which — per its own documented limitation at `elaborator.ex:4732` ("`resolve_free` only ever yields the NULLARY `{:ctor, atom, []}`") — returns `{:ctor, atom, []}` for *any* constructor name regardless of its declared arity. For an arity-1 constructor like `S` that zero-arg term is ill-formed, and the kernel's arity check (`check_ctor_app`, `lib/cure/core/kernel.ex:525-537`, reached from the `{:ctor, name, args}` clause of `Kernel.infer/2`) rejects it with `{:error, :ctor_arity}` before Core is even produced — emit is never invoked. So today `let f = S` or `map(S, xs)` fails to elaborate for *every* positive-arity constructor in the language; the Bool precedent never surfaces this because both of Bool's constructors are nullary (`bool_ctor?`/`bool_atom` only ever handle the `args == []` shape, `emit.ex:158-163`). Landing rule 4 therefore requires an **elaborator-layer** fix — extending `resolve_free` (or its call site) to eta-expand a bare positive-arity constructor into `{:lam, dom, {:ctor, name, [{:var, 0}, …]}}` before the kernel ever sees it, not a new emit-layer hook site. Once eta-expanded, the result is an ordinary fully-applied `{:ctor, ...}` term nested inside a `{:lam, ...}` — the existing (§2.1-extended) ctor-lowering clause already emits that correctly with no further emit-side work; `Z` needs no such treatment (already nullary, already a value). The plan must scope the eta-expansion fix generally (any positive-arity builtin ctor resolved bare), not special-case `S`, and must budget it as elaborator work, not emit work.

No new IR node, no new registration mechanism, no `erase.ex` change. This mirrors Idris precisely: the ZERO/SUCC decision is a per-constructor nominal flag consumed by the code generator, nothing upstream knows.

### §2.2 Lowering fine points

a. **Clause order/guards.** The Z-branch lowers to the literal pattern `0`; the S-branch lowers to a fresh variable pattern with guard `when N > 0` (not a bare catch-all), so emitted clause order cannot silently change semantics regardless of the order branches arrive in from Core, and a representation bug (a negative int reaching a Nat case) crashes loudly rather than binding `k = -1` and continuing wrong. The kernel guarantees a well-typed Nat scrutinee, so the guard is belt-and-braces, not load-bearing. (This guard populates emit.ex's clause guard-slot for the first time — see the verified new-territory note in point c, which covers both the guard and the body-shape implications together.)

b. **Deep patterns need no special handling.** Core `:case` is single-level (the matrix compiler splits nested patterns into single-level cases before elaboration), so `S(S(m))` arrives as two nested single-level cases and lowers compositionally to two `- 1` bindings.

c. **Frame accounting — and two new erl_syntax shapes emit.ex has never produced before.** The S-branch body's de Bruijn frame counts the field (index 0 = the bound predecessor, per the comment at `emit.ex:305-307`, immediately preceding `branch_clause/3` at `emit.ex:308-333`). The S-field must therefore still be a bound BEAM variable, bound by `K = N - 1` — but Erlang clause patterns/guards cannot perform arithmetic and bind the result, so `K = N - 1` cannot live in the pattern or the guard; it must be the clause **body's first statement**, making the S-branch's body a 2-element form list `[bind_form, body_form]` (`{match, line, {var,line,:K}, {op,line,:-,{var,line,:N},{integer,line,1}}}` followed by the existing lowered body), with the rest of the body lowering proceeding unchanged against the same frame. **Verified: this is genuinely new territory for `emit.ex`.** Every `{:clause, …}` it builds today (`emit.ex:133`, `:199`, `:332`) hard-codes an empty guard list (`[]`) and a **singleton** body `[body_form]` — nothing in the current codebase populates a clause's guard slot or produces a multi-statement clause body. Rule 2 needs both for the first time: the `when N > 0` guard (§2.2a) populates the guard slot; the `K = N - 1` bind makes the body two statements instead of one. This is the single trickiest edit; the plan carries a dedicated red test (nested `S(S(m))` match whose body uses `m`) and should treat the guard-slot and multi-statement-body shapes as their own red-test-worthy sub-cases, not incidental variations on the existing pattern-only clauses.

d. **`Z()` pattern ≡ literal `0`.** Once Nat is an int at runtime, a `Z()` constructor pattern and an integer-literal `0` pattern (the `try_literal_match` path over primitive scrutinees, which is Int-typed and unrelated to Nat today) coincide as the BEAM pattern `0`. This is an identity to state, not machinery to build — Nat-typed scrutinees never take the literal-chain path and Int-typed scrutinees never take the ctor path.

### §2.3 The generics gap — resolved by parametricity, no monomorphisation

The foundation spec's open question (lines 228-241) asks how a function generic over `a: Type`, instantiated at `Nat` in one call and another inductive elsewhere, reconciles representations in one unspecialized body. Resolution: **the Int representation is global and uniform, and no reconciliation is needed**, because on a dynamically-typed target the only operations an unspecialized body can perform on an `a`-typed value are opaque (pass, store, return, put in a container). Constructor-matching a scrutinee requires the elaborator to know its type is the `Nat` family — a bare type-parameter-typed scrutinee cannot elaborate `Z()`/`S(k)` arms (there is no `:vdata` family to dispatch on). So:

- A `Pair(Nat, Nat)` or `Lst(Nat)` simply holds small ints where it held tuples; the container's own representation is untouched.
- Every site that CAN deconstruct a Nat knows it statically (its scrutinee type elaborated to the `:nat` family), which is exactly the set of `:case`s §2.1 lowers.
- This matches Idris: ZERO/SUCC flags are global, and Idris's Nat hack ships with no monomorphisation.

The spec pins this with a polymorphic-container test (a generic pair holding Nats, constructed and deconstructed through generic code, runtime shape `{:MkP, 0, 2}`-style). If the plan-time sweep finds ANY elaborator path that lets a ctor pattern match a type-parameter-typed scrutinee (refining `a := Nat`), that is a STOP-and-report — it would falsify the parametricity argument and the design needs the operator.

### §2.4 Nominal, not structural

The rep applies only to the family-id registered under `Inductive.builtin(env, :nat)` — the prelude `Std.Nat` (foundation lines 138-155). A locally redeclared `type Nat = Z | S(Nat)` keeps tuples, silently (the foundation's explicit choice). Consequences pinned as regression tests, not changed:

- `test/cure/compiler/dependent_vec_codegen_test.exs` test 1 uses a local Nat: its tuple-shape assertions **stay** and double as the nominal-no-op pin. (Its test 3 is canonical-Nat via stdlib-from-disk and carries the batch's only three flips — see §4's execution-time correction; the file is mixed, not uniformly do-not-touch.)
- The `phase35/` ESP32 demos redeclare Nat locally and therefore get no benefit until they `use Std.Nat`; the recommended lint/compiler note stays out of scope (the foundation spec states this stance inline in its own "Nominal, not structural" section, lines 150-155 — the foundation doc has no numbered "§6"; this document's own §6 below is where the exclusion is formally listed for this batch).

### §2.5 What does not change (the layering pins)

- **Kernel and eval untouched:** the kernel keeps checking and reducing Nat as the inductive; `Eval.eval/2` keeps producing `{:vctor, :S, [...]}`-shaped values (`lib/cure/core/eval.ex:42`: the `{:ctor, name, args}` Core-term clause evaluates to the `:vctor`-tagged value, not the `:ctor`-tagged term — the two are related but distinct tags, term vs. value). Every `test/cure/core/*` pin (size_change, cycle_rule, conv, certify, unify_indices, builtins_*) must pass unchanged — they are the regression guard that the "checking-time fiction" stayed intact.
- **Erased Core untouched:** `erase.ex` still emits `{:ctor, :Z, []}` / `{:ctor, :S, [kept]}`; representation is chosen at BEAM lowering. Tests asserting on erased-Core shapes (e.g. `test/cure/elab/global_namespace_soundness_test.exs:179-189`) must pass unchanged.
- **Bool behavior untouched**, including `connective_inline` (`emit.ex:215-235`).

### §2.6 Arithmetic

`Std.Nat` arithmetic defs (recursive `:case` over Nat) compile unchanged and now operate on ints: correct by the representation-agreement property, O(1) space, still O(n) time. Inlining known Std.Nat ops to native `+`/`-` (the `connective_inline` precedent) is an explicit non-goal/follow-up — v1 lands the representation, not the arithmetic acceleration. (Idris's `NaturalToInteger`/`IntegerToNatural` identity pragmas are the analogous follow-up surface.)

## §3 Trust boundary and verification

This is the foundation's **Phase 2: untrusted, ungated** (lines 268-272). A lowering bug yields a wrong runtime value, never an unsound acceptance — no TCB review gate applies (and none is available: nothing under `lib/cure/core/` may change). Verification is:

1. Strict red-green unit tests (per lowering rule).
2. **Representation-agreement property (foundation line 224):** a new Antigen assay (`elab/nat_rep`) with a seeded generator of closed, well-typed `Std.Nat` programs (bounded-depth arithmetic + matching + HOF-S/Z + container round-trips): for each, the kernel's oracle result (decoded `{:ctor,:S,…}` spine → integer) must equal the BEAM execution result (already an integer). **Mechanism, verified:** the oracle call is NOT bare `Eval.eval/2` (`lib/cure/core/eval.ex`) — that function always treats a `{:global, name}` head as an opaque neutral (`eval.ex:53-54`: "Opaque until the global is certified total... `{:vneutral, {:nglobal, name}}`") and never unfolds it, so alone it cannot reduce a recursive call like `plus(S(Z()), S(Z()))` to a final ctor value; it would get stuck. The actual reduction-capable oracle is the kernel's certified-δ normaliser, `Cure.Core.Normalise.nf/3` with `delta: :certified` (`lib/cure/core/normalise.ex:97-231`), which DOES unfold a global head once `Env.certified?/2` (`inductive.ex:84-86`) says so. This is available for free, not a new prerequisite: every def is auto-submitted for totality certification during ordinary elaboration (`maybe_certify/2`, `lib/cure/elab/declarations.ex:270`), and `Std.Nat`'s structurally-recursive arithmetic (`lib/std/nat.cure`) is exactly the shape the size-change termination checker already certifies. **Signature, verified:** `nf/3`'s actual shape is `nf(ctx, term, opts)` (`normalise.ex:36-37`, `@spec nf(Context.t(), Cure.Core.Term.t(), opts()) :: Cure.Core.Term.t() | :fuel_exhausted`) — it takes a `Context.t()`, not the signature directly; for a closed term the plan should build that context via `Context.empty(sig)` (`context.ex:29`, which stores `sig` in the context's own `signature` field, `context.ex:15`). So the plan should name the oracle call precisely as `Normalise.nf(Context.empty(sig), term, delta: :certified, mode: :nf)`, not "kernel eval" generically and not `Normalise.nf(term, sig, ...)` — a reader could otherwise reach for `Eval.eval/2` (stuck neutral term, wrong function) or pass `term`/`sig` in the wrong argument positions (wrong arity/type, a `Context.t()` is required first). Kernel normalisation is the oracle — it is the trusted semantics; emit is the system under test.
   **Plumbing note (verified):** no existing Antigen assay currently does both halves of this comparison — `lib/antigen/assays/elab.ex` and its sibling assay/generator files use `Eval.eval` only for type-level evaluation (Conv comparisons), and a repo-wide `grep` for `compile_and_load`/`Emit\.` under `lib/antigen/` returns zero hits (BEAM compile-and-execute is exercised only from unit tests, e.g. `test/cure/elab/guard_lint_test.exs:120`). So `elab/nat_rep` genuinely combines two previously-separate capabilities for the first time in Antigen; the plan should budget it as new integration work, not as reuse of an existing dual-execution assay pattern.
3. The full suite including oracle replay (differential fixtures pin verdicts, not runtime shapes — replay must stay green untouched).

## §4 Test-migration policy (the deliberate behavior change)

Runtime Nat shapes change from `{:S, {:S, :Z}}`-style tuples to ints — a spec'd, operator-authorized behavior change (foundation §3), so the affected **BEAM-runtime** pins are updated as part of the feature's red-green, under a strict protocol:

- **Flip:** only assertions on `apply(mod, …)` results (and closure-application results) whose values are values of the **canonical `Std.Nat`** (the `@builtin(:nat)`-tagged family reached via `use Std.Nat`) — `{:S, :Z}` → `1`, `:Z` → `0`, values nested in containers likewise (`{:MkP, :Z, {:S,{:S,:Z}}}` → `{:MkP, 0, 2}`).
- **Verified correction (this review): the obvious scout-inventory candidates are NOT flip candidates.** An exhaustive check of every `test/cure/elab/*.exs` file whose fixtures declare a `Nat` and assert tuple/atom shapes (46 files, via `grep -rl "type Nat = Z | S(Nat)"`) shows **all of them** declare Nat locally in the fixture source itself (e.g. `@nat "mod M\n  type Nat = Z | S(Nat)\n"`) rather than `use Std.Nat` — including every file this spec's earlier draft named as a flip candidate: `polymorphic_function_test.exs:23,65`, `auto_generalize_test.exs:20`, `first_class_function_test.exs:21`, `nested_pattern_test.exs:20`, `guard_test.exs:16`, and `guard_lint_test.exs:104` (whose `@nat` fixture is likewise `mod M\n  type Nat = Z | S(Nat)\n`, no `@builtin`, no `use Std.Nat`). Per §2.4's own nominal-not-structural rule, every one of these is a **local-Nat fixture** — it keeps tuples silently and must NOT flip; flipping any of them would break a currently-correct assertion, not fix a stale one. A cross-reference of every file that DOES `use Std.Nat` anywhere in `test/` (`auto_prelude_test.exs`, `type_shadowing_test.exs`, `test/cure/compiler/shadow_codegen_test.exs`, plus the `test/oracle/shadow/*.cure` fixtures) against every file with a BEAM-runtime `apply(mod, …)`/`compile_and_load` call turns up **zero overlap** — no test in the current tree combines canonical `Std.Nat` with a runtime-shape assertion. So the actual flip bucket, as of this review, is **empty**; the int-shaped runtime assertions this feature needs are supplied by the feature's own new red-green tests (§3 item 1), not by flipping pre-existing pins.
- The plan must still re-grep the then-current tree at plan time (the tree can change between this review and implementation) and must still enumerate every file+line found, with the same STOP-and-report protocol: any pin that doesn't flip exactly as predicted, or any pin not on the list that fails, halts for operator input. The correction above is a fact about the tree at review time, not a license to skip the plan-time re-scan.
- **Execution-time correction (2026-07-08, executor STOP finding — orchestrator-adjudicated): the flip bucket is NOT empty; it has exactly one member the review's grep was structurally blind to.** `test/cure/compiler/dependent_vec_codegen_test.exs` is a MIXED file: its test 1 uses a local `type Nat` fixture (correctly classified, stays tuples), but its test 3 compiles the real stdlib **from disk** (`lib/std/nat.cure` with `@builtin(:nat)`, `lib/std/bounded.cure`, `lib/std/vector.cure` whose line 9 is `use Std.Nat`) — so `Std.Vector`'s Nat values are CANONICAL and flip to ints. The review's cross-reference greped `test/` for `use Std.Nat` and could never see canonical Nat arriving via stdlib-source compilation inside the test. Three assertions flip (and only these): line 85 `replicate`'s first argument `{:S, {:S, :Z}}` → `2`; line 98 `count(xs) == {:S, {:S, :Z}}` → `== 2`; line 99 `length(xs) == {:S, {:S, :Z}}` → `== 2`. Everything else in test 3 is representation-correct as written: `lookup`/`update`/`set` indices are `Bounded(n)` values (`:First`, `{:Next, :First}`) — a separate family the `:nat`-only nominal rule does not touch; Vector/Bool results are not Nats. The flips land in the same commit as the emit change, per this section's same-commit rule. Any FURTHER pin failure beyond these three remains a fresh STOP.
- **Do not touch:** erased-Core-shape assertions; all `test/cure/core/*`; local-Nat fixtures — this now explicitly includes the ~46 `test/cure/elab/*.exs` files enumerated above (not just `dependent_vec_codegen_test.exs`, which remains the canonical example, §2.4); oracle `verdicts.json` (verdicts are accept/reject, representation-independent).
- The flips land in the SAME commit as the emit change that necessitates them (a green tree at every commit), with the flip list reproduced in the commit message body or the plan checked off per file.

## §5 Idris divergence

None. This aligns Cure WITH Idris (the Nat hack is Idris-sourced); oracle relations are unaffected because the oracle compares elaboration verdicts, not runtime representations.

## §6 Non-goals

- Monomorphisation / specialization machinery (§2.3 shows it is not needed).
- Native inlining of Std.Nat arithmetic (`connective_inline`-style) — follow-up.
- GMP/bignum kernel acceleration (foundation: type-level Nats are small; kernel unchanged).
- The `use Std.Nat` lint / compiler note for locally-redeclared Nats (foundation: out of scope).
- `Bounded`/`Fin` as a further native-int builtin (queued separately in the stdlib-dependent-expansion plan).
- Any change to `lib/cure/elab/erase.ex` representation behavior, `lib/cure/core/*`, `lib/cure/types/*`, `lib/cure/compiler/*` (two-pipeline discipline; `test/cure/compiler/dependent_vec_codegen_test.exs` is a test, not that pipeline's code).

## §7 Acceptance criteria

1. A `use Std.Nat` program's runtime Nats are BEAM ints: `S(S(Z()))` evaluates to `2` via `apply`; matching `S(k)` binds `k = 1`; a body using a two-deep `S(S(m))` binding computes correctly.
2. First-class `Z`/`S` work as values: passing `S` to a HOF and applying yields ints. (Prerequisite: the `resolve_free` eta-expansion fix in §2.1's third bullet — today this doesn't elaborate at all, for any positive-arity constructor.)
3. A generic container holding Nats round-trips through unspecialized generic code with int elements (§2.3 pin).
4. A locally-redeclared Nat still produces tuples (§2.4 pin, existing fixture unchanged).
5. Antigen `elab/nat_rep` representation-agreement assay green: the kernel-normalisation-decoded integer (`Normalise.nf(..., delta: :certified)`, §3 item 2) == BEAM integer on the generated corpus.
6. `git diff` of the landed work: zero changes under `lib/cure/core/`, `lib/cure/types/`, `lib/cure/compiler/` (code), and `lib/cure/elab/erase.ex`; every `test/cure/core/*` and erased-Core-shape test unchanged and green.
7. Full gate green: `mix test test/antigen/` then full `mix test` (with oracle replay), zero failures; every §4 flip matches its plan-time prediction.
