# Antigen fixture & corpus robustness hardening — design

**Status:** approved (design gate). Autopilot run on `autopilot/antigen-tier-b` (stays on this worktree per operator preference). Written after merging `autopilot/lean-shape-matching` (112 commits) into `antigen-tier-b`.

## 1. Motivation

Three robustness gaps, bundled because they all harden the Antigen generator/corpus fixtures against non-determinism and latent decode failure:

1. **A flaky mutation-generator test** (`test/antigen/generators/mutation_test.exs`) that fails only intermittently in the full suite. Investigation (below) shows the *described* mechanism does not match the code, so the fix is **defensive**: make every generator invariant hold **by construction** and rewrite the probabilistic / kernel-sampling assertions to be **draw-independent**, killing any latent seed-flake in the file regardless of which assertion it was.
2. **`@known_atoms` is incomplete** (`lib/antigen/challenge.ex`) — a latent decode-safety gap surfaced while making the corpus human-readable. Confirmed missing (audited against the real hazard mechanism, §3.1): `:data_split`, `:reify_distinct`, `:reify_eq`. Masked in the full suite (generator modules intern their literal atoms at load), but a bare-process decode **raises** `ArgumentError` when `Challenge.from_pieces/7` (or `decode_record`'s `kind`/`label` conversion) runs `String.to_existing_atom/1` on a scaffold-carried name that isn't pre-interned. See §3.1 for why this is *not* "a raw atom inside the `[:safe]` blob" — that specific framing turned out to be wrong.
3. **Two corpus-format coverage facts** the readable-corpus work surfaced — the fault value-grammar is wider than flat atoms (`scope` int-pair; `:universe` term-valued heads), and there are **four** committed corpora, not three — worth **locking with regression guards** so a future change can't silently regress them. The fourth, `test/antigen/reach_reify_split.sexp` (used by `test/antigen/reify_split_gap_reach_test.exs`), was missed by both the readable-corpus migration and this design's first draft; it is still in the **legacy Base64 format** (pieces and note un-migrated) — confirmed by direct inspection, not assumed — and needs to be brought into scope (migrated, §4c) as part of this work.

### 1.1 Investigation findings (grounding — not hypothetical)

- The handoff points at `mutation_test.exs:36` (the `:index` arm asserting `f.expected_head != f.injected_head`). That reads a **static** fault-map constant — `index_mismatch` is hard-coded `expected_head: :Z, injected_head: :S` (`mutation.ex:58`); `:Z != :S` is always true and that test **never samples StreamData**, so it cannot seed-flake.
- Every `build/2` operator uses a **fixed structural mismatch**, not a drawn constructor. A 600-draw-per-operator probe found **0 kernel-accepted (no-op) terms**. A 15-seed sweep of `mutation_test.exs` in isolation is **all green**. The banked corpus is clean (all fault heads distinct; 13/13 distinct mutant terms).
- The one genuinely draw-and-kernel-dependent assertion is the **uncontaminated-control** test (`mutation_test.exs:82-85`): it samples 15 random wrapper stacks around a well-typed `Nat` inner and asserts the kernel **accepts** each. Contamination can only arise if a wrapper's **filler** (`gnat(ctx) = Term.gen_term(ctx, Nat)`) is ever *not* a well-typed `Nat` — which would make the stack ill-typed independent of the inner, failing the assertion. This is the plausible flake surface **and** a latent generator-soundness defect (a "rejected" mutant rejected for the wrong reason).

## 2. Part 1 — Mutation generator: construction guarantees + deterministic tests

### 2.1 Construction guarantees (generator side)

- **Rejection is filler-independent.** For every operator in `Mutation.operators()`, the mutant `infer`-rejects *regardless* of any drawn well-typed filler — the wrongness lives in the fixed structural mismatch, never in a draw. Audit `build/2`; today this holds (fixed heads). Document it as an invariant; if any operator is found where a draw could make the term well-typed, restructure it (fix the mismatch site, or reject-sample) so rejection is guaranteed.
- **Wrappers are non-contaminating.** For every wrapper in `Mutation.wrappers()`, a **well-typed `Nat` inner** yields a **well-typed** stack. Each wrapper is Nat→Nat with a `Nat` filler, so this reduces to: **`gnat(ctx)` / `Term.gen_term(ctx, Nat)` must only ever produce well-typed `Nat` terms.** Verify this is a construction guarantee of the lazy `Term` generator. If it can produce an ill-typed / stuck filler (the flake root), fix it — either constrain the filler to a provably-well-typed subset, or reject-sample fillers that fail a cheap well-typedness check — so contamination is impossible by construction. **Checked (not just asserted): 5,000 draws of `Term.gen_term(Context.empty(env), Nat)` — all 5,000 both `infer`-accept and convert to `Nat`, zero bad. 3,000 draws of `Mutation.deepen(ctx, {:ctor,:Z,[]}, 8)` (max depth) — all 3,000 stacks `infer`-accept, zero contaminated.** This lands squarely in the §8 "finds nothing to fix" branch: the generator is already sound, so this construction guarantee needs no code change, only the documentation/invariant capture below and the deterministic test rewrite in §2.2. Item 3 of §5 is therefore not expected to fire on this run — keep it in the plan as the standing regression contract (if the invariant ever breaks, that's the red test that will catch it), not as a step this run's implementer needs to write speculatively.

### 2.2 Deterministic tests (test side)

Rewrite the flaky / probabilistic assertions in `mutation_test.exs` to be **draw-independent**:

- **Uncontaminated control** (`:82-85`): replace 15 random `deepen` samples with **deterministic per-wrapper enumeration** — for each wrapper kind, build the stack once with `inner = {:ctor,:Z,[]}` (well-typed `Nat`) and a **fixed** filler, assert the kernel **accepts**. A companion deterministic check: each wrapper around an intrinsically-ill-typed inner (`{:fst,{:ctor,:Z,[]}}`) **rejects**. No sampling, no kernel-on-random-draw.
- **Every operator rejects** (`:9-21`): keep the kernel-rejection check but make it deterministic — one representative construction-guaranteed draw per operator (a fixed filler / pinned generator), not 20 random samples whose acceptance the kernel decides.
- **Diversity asserts** (`≥5 fault kinds`, `≥4 wrapper kinds`): replace "sample N and hope the count is high enough" with **deterministic reachability** — assert each operator/wrapper is *individually* reachable (enumerate `operators()`/`wrappers()` and show each is produced), rather than a probabilistic count over a random sample.

> The witness-invariant test (`:23-46`) is already deterministic (reads static fault fields); keep it, and it doubles as the check that §2.1's fixed-mismatch invariant holds.

**Where sampling is inherent** (e.g. a test that genuinely must exercise the random generator), pin a fixed seed and document why, rather than relying on the ambient suite seed.

## 3. Part 2 — `@known_atoms` completeness + bare-process decode guard

### 3.1 Audit + add

**The hazard mechanism, precisely (verified against the code, not assumed).** `to_pieces/1` stringifies every atom-valued field with `Atom.to_string/1` before it goes into the `scaffold` map that gets `[:erlang.term_to_binary/1]`-encoded — so, empirically, **no committed record's `scaffold` blob contains a raw Erlang atom today**; `decode_scaffold`'s `binary_to_term(_, [:safe])` never actually has an un-interned-atom to choke on for any *current*-format record. The real hazard lives one step later, in `Challenge.from_pieces/7` (plus `kind`/`label` in `Corpus.decode_record/1`), which calls `String.to_existing_atom/1` on scaffold-carried **strings** to rebuild: `kind`, `label`, `sig`, `def_name` (`:indexed_case`/`:rewrite_eq`), `fam_name`/ctor `name`/`arg_names`/`quantities` (`:family` and nested inside `:indexed_case`/`:rewrite_eq`), and `def_group` `names`/`focus` (`:def_group`/`:forcing_pair`/`:stuck_elim`). *This* is the set the audit must scan — not "atoms found by decoding the blob" (that scan is always empty and gives false assurance; verified by direct probe).

Three more fields are **not** part of this hazard, despite looking like plausible candidates: `assay` stays `String.t()` end-to-end (`Challenge.t()`'s field type, `Corpus.decode_record`'s use of `m["assay"]` directly) and is never atom-converted, so assay-name strings never need `@known_atoms` membership. Term-**piece** atoms (`{:global, n}` / `{:ctor, n, …}` / `{:data, n, …}` / `{:prim, op, …}`) are recovered by `Cure.Core.Serialize.decode/1` via `String.to_atom/1` (which **mints**, never raises) — piece atoms are never a decode hazard regardless of `@known_atoms` membership, so the audit should not scan pieces. And a current-format mutant's readable `fault=` field is decoded by `Corpus`'s own hand-rolled reader (`decode_fault`/`dec_fault_val`), which also calls `String.to_atom/1` for both keys and values (**mints**, never raises) — so fault-kind/witness/head atoms are *not* a hazard for any record migrated to the current format. (They *would* be a hazard for a legacy mutant record with `fault` still embedded inside the Base64 `scaffold` — that path goes through `[:safe] binary_to_term`, not `decode_fault` — but no committed record is in that state: all 13 `mutant_term` records across the four corpora carry an explicit `fault=` field, confirmed by direct inspection.)

Audit every committed record (all four corpora, §1 item 3) for the string values of the fields named above, plus every module under `lib/antigen/generators/` for `def_name`/family/ctor literals reachable in a future banked record via those same fields, and add every missing name to `Challenge.@known_atoms`. Confirmed missing today (found by decoding every committed record's scaffold field-by-field per the schema above and diffing the string values against `@known_atoms`, not by grepping raw text — the scaffold field is itself Base64):
- `:data_split` (`def_name`, `corpus.sexp`, from `Indexed.data_split_validation/1`)
- `:reify_distinct` (`def_name`, `corpus.sexp`, from `Indexed.reify_collapse_distinct/1`)
- `:reify_eq` (`def_name`, `reach_reify_split.sexp`, from `Indexed.reify_eq_indexed_reach/1`)

Two names in the original handoff turned out **not** to be real hazards and are dropped from the missing-list: `:boom` does not appear in any committed record at all (checked directly), and even if `Generators.Stub` produced one that got banked, `{:global, :boom}` is a Term-piece atom — minted on decode, never a hazard. `:stuck_elim_delta` does appear (5×, `corpus.sexp`) but only as the `assay=` field's string value, which is never atom-converted — not a hazard either. The audit must be exhaustive over the corrected hazard set above, not just the three names originally suspected.

### 3.2 Bare-process decode regression test

Add a test that, in a context where **only** `Challenge.__known_atoms__()` is forced (generator/assay modules **not** relied on to intern their literals), decodes **every** record of **every** committed corpus (`seeds.sexp`, `corpus.sexp`, `reach.sexp`, `reach_reify_split.sexp`) and asserts all succeed (no `decode_error`, no raised `ArgumentError`). This permanently catches the missing-atom class. (`reach_reify_split.sexp` decoding here does not require it to be migrated first — `decode_record` dual-reads legacy Base64 pieces; only §4(c)'s readable-format guard requires migration.)

> Implementation note: the test cannot truly unload already-loaded modules within one BEAM, but it **can** assert the decode contract holds after forcing only `__known_atoms__()`, and — more strongly — assert that every hazard-string named in §3.1 (`kind`, `label`, `sig`, `def_name`, family/ctor `name`/`arg_names`/`quantities`, `def_group` `names`/`focus` — **not** Term-piece atoms, which `Serialize.decode` always mints, and **not** `assay`, which is never atom-converted) is a member of `@known_atoms` (a static membership check over the corpus), which is what actually guarantees bare-process safety. The plan picks the concrete assertion; the membership check is preferred as it is deterministic and independent of load order. Implement the check by decoding each record's `scaffold` field with plain (non-`:safe`) `binary_to_term` and pulling the specific string sub-fields per the kind-indexed schema in §3.1 — **not** by recursively collecting already-materialized atoms from the decoded blob, which is always empty under the current (fully-stringified) scaffold format and would silently pass even with real gaps (verified: this naive approach found 0 of the 3 real missing names above).

## 4. Part 3 — fault-schema + corpora consistency guards

- **(a) Fault value-grammar lock.** Strengthen the fault-codec coverage: assert `decode_fault(encode_fault(f)) == f` for a fault of **every value shape the generators actually emit** — enumerated by calling `Mutation.build/2` for each operator (+ a deep `deepen` fault with `depth`/`wrap_path`, + a `Conversion.conv_reject` carrier fault), not hand-written maps. Locks the atom / int / `nil` / int-pair / list / Core-term grammar the readable-corpus work introduced. **Checked: this codec already round-trips every one of these generator-emitted shapes correctly today** (verified by building the actual fault maps from all 7 `Mutation.operators()` + a depth-3 `deepen` + `Conversion.conv_reject`, and round-tripping each through `encode_record`/`decode_record` — zero mismatches). So unlike the other items in §5, this one is **not** red-then-green: `lib/antigen/corpus.ex` needs no change (confirmed by §6's "Untouched"), and the new test is a coverage/regression lock against *future* codec/generator drift, not a fix for a current bug. Write it as a plain regression addition, not a red-test-first step — there is no red state to reach here.
- **(c) Corpora-readable guard.** A test asserting every committed corpus (`seeds.sexp`, `corpus.sexp`, `reach.sexp`, `reach_reify_split.sexp`) is fully in the readable format — every piece body starts with `(` (no Base64 pieces), and every record decodes — so a future un-migrated record fails CI instead of silently regressing readability. `reach_reify_split.sexp` is currently **not** readable (confirmed: its one record's pieces and note are still legacy Base64), so this guard starts red for that file until it is migrated — migrate it in the same commit (`mix antigen.migrate test/antigen/reach_reify_split.sexp`; the task is proven idempotent and lossless on already-new-format input and dedup-key-preserving on legacy input, per `corpus_test.exs`'s existing migration test) so the guard goes green across all four files, not three.

## 5. Testing (TDD, per Stage 4)

Two items are genuinely red-then-green (write the test, watch it fail for the stated reason, then make the minimal implementation/data change to turn it green): **item 4** (`@known_atoms` additions) and **item 6** (migrate `reach_reify_split.sexp`). The rest — **items 1, 2, 3, 5** — are regression-locks: per §2.1/§4a's direct checks, the invariants they assert already hold today, so write them as plain test additions expected to pass on first run, not as speculative red-first steps (each item's note below says why). Don't force a red state that doesn't exist — if any of these unexpectedly fails on first run, that is itself a new finding (the checks in §2.1/§4a were wrong), not something to route around by weakening the assertion.

1. **(Part 1)** Deterministic uncontaminated test — every wrapper accepts a well-typed inner with a fixed filler; every wrapper rejects an intrinsic-fault inner. Draw-independent. (Rewrites an existing probabilistic assertion — "red" here means the *old* probabilistic test is deleted/replaced, not that the new deterministic assertion is expected to fail; per §2.1's check it will pass immediately, which is correct — it is locking a guarantee that already holds, the same category as item 5.)
2. **(Part 1)** Deterministic per-operator rejection + per-operator/per-wrapper reachability (replacing the probabilistic diversity asserts). Same category as item 1: a determinism rewrite of an already-correct guarantee, not a bug fix.
3. **(Part 1)** If §2.1 finds `gnat`/`gen_term(Nat)` can produce a non-well-typed filler: a red test exhibiting a contaminated stack, green after the generator fix. Per §2.1's check (5,000 + 3,000 draws, zero contamination) this is **not expected to fire on this run** — keep it as the standing contract, not a step to write speculatively.
4. **(Part 2)** Static membership: every hazard-string (§3.1's kind-indexed schema, not a raw atom scan) in every committed corpus record ∈ `@known_atoms` — genuinely RED for `:data_split`/`:reify_distinct`/`:reify_eq` (verified: these three are absent from `@known_atoms` and present in committed records today), green after §3.1's additions.
5. **(Part 3a)** Fault codec round-trips every generator-emitted fault shape. **Not a red test** — verified the codec already round-trips every real generator-emitted shape today (§4a); write this as a coverage/regression addition against future drift, expected to pass on first run.
6. **(Part 3c)** All four corpora are readable + decode. Genuinely RED for `reach_reify_split.sexp` (confirmed still-legacy, §1 item 3) even though the other three already pass; green once that file is migrated (§4c).
7. **Full suite once** (Stage 5) — all green; run `mutation_test.exs` across several seeds to confirm determinism.

## 7. Non-goals (YAGNI)

- Changing the corpus on-disk format further (done).
- A `to_existing_atom` corpus decoder (separate, deferred item).
- Reproducing the exact original flake (falsified against the code; the fix is construction-by-design, which subsumes it).
- Broad generator redesign — only the minimal change needed to make the audited invariants hold by construction.
- Re-banking / regenerating corpora (the guards validate the existing migrated files). Running the existing, already-proven-idempotent `mix antigen.migrate` on `reach_reify_split.sexp` (§4c) is a format rewrite of already-committed data, not re-banking — it adds no new challenges and changes no dedup key.

## 8. Risks

- **§2.1 confirmed nothing to fix** (the generator is already sound — 5,000/3,000/600-draw checks, zero violations; no longer an open question by the time this design is executed). So Part 1 is purely a test-determinism rewrite — still valuable (kills the seed-flake), and the residual risk is only that the "flake" recurs from a source outside this file, or from a generator input space the samples didn't cover. Mitigation: the deterministic rewrites remove *this file* as a flake source; if it recurs elsewhere the failure will point there.
- **Atom audit misses one**: mitigated by the static membership test (§3.2), which scans every hazard-string field (§3.1's schema) of every committed record, so any name a real record actually carries in one of those fields is checked — the test fails if the audit was incomplete. (It does not, and does not need to, scan piece/assay/fault-field content — §3.1 established those are never `String.to_existing_atom` targets.)
- **Determinism rewrite weakens coverage**: enumerate-each-reachable is *stronger* than probabilistic-count (it proves each case, not just the aggregate), so coverage is preserved or improved.
