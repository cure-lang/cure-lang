# Antigen directed generation — design (Run A)

**Status:** approved (design gate — operator batch-approved A/B/C/D). Autopilot on `autopilot/antigen-tier-b`. Pure-Antigen: **no `Cure.Core.*` (TCB) edits.**

## 1. Motivation

A `--count 50000` explorer run found **0 infections** while banking a large seed set — evidence that undirected StreamData generation *plateaus*: dedup collapses to a coarse feature vector (`Coverage.key = {ctors, bucket(depth), flags, label}`), so past a few thousand rounds most draws re-cover buckets already seen. The fix is to make generation reach **deeper and more diverse** shapes without touching the kernel. Three independent, pure-Antigen levers:

1. **Coverage-vector enrichment** — the dedup/health key is too coarse; refine it so distinct-but-similar terms stop colliding and the health gate sees real diversity.
2. **Corpus-backed fillers (crossover)** — reuse real banked terms as well-typed fillers, reaching term shapes fresh random generation rarely hits.
3. **Health-adaptive biasing** — close the existing health loop so generation steers toward the weakest vertical instead of drawing uniformly.

## 2. Part 1 — Coverage-vector enrichment

`Coverage.key/1` currently returns `{ctors, bucket(depth), flags, label}` where `ctors` is the *set* of constructor names and `bucket(depth)` is a coarse depth band. Two distinct terms with the same constructor *set*, depth band, flags and label are treated as covered-equivalent — collapsing genuinely different structures.

**Change:** enrich the feature vector with two cheap, plateauing structural signals (both bounded, so the key space stays finite and dedup still converges):

- a **former histogram bucket** — for each Core former class present (`:lam`/`:pi`/`:app`/`:case`/`:ctor`/`:data`/`:eq`/`:rewrite`/`:prim`/leaf), a *presence* bit or small count bucket (0 / 1 / many), capturing *shape mix* not just constructor identity;
- a **binder-depth bucket** — max nesting depth of binders (`:lam`/`:pi`/`:sigma`/`:case`-branch), bucketed, distinct from the existing overall term-depth bucket.

**Shape (arity-preserving):** `Coverage.key/1`'s return stays a **4-tuple** `{ctors, bucket, flags, label}` — the two new signals are encoded as additional atoms folded into the existing `flags` `MapSet` (e.g. `:former_lam_present`/`:former_case_many`/`:binder_depth_b3_5`, alongside the existing `:app_present`/`:has_shadowing`-style flags), not as new top-level tuple positions. This matters beyond style: `Runner.coverage_flags/1` (`lib/antigen/runner.ex`) already destructures `Coverage.key/1`'s result positionally — `{_ctors, _bucket, flags, _label} = Coverage.key(c)` — for the health-gate coverage report; growing the tuple's arity would `MatchError` there (a Part-1 change silently breaking Part-3's-listed file) unless `runner.ex` is *also* updated, which §6's Files list does not attribute to Part 1. Keeping arity at 4 avoids that coupling entirely — `Runner.coverage_flags/1` keeps working unchanged, and picks up the richer flag set in its coverage report as a side benefit. (Existing `coverage_test.exs` assertions on `bucket`/membership-in-`flags` are unaffected by this shape choice; only the enrichment's own new-key/new-flags assertions are additions.)

The key stays a small tuple of bounded-cardinality features (spec §7.2's "plateauing feature vector" property is preserved — it must still saturate, not grow unboundedly). `key_string/1` extends to render the new fields. `Coverage.terms_of/1` is unchanged. **Backward-compat (corrected):** `Corpus.dedup_key(c, :seed)` *is* `Coverage.key_string(Coverage.key(c))` — every committed `seeds.sexp` record's `key=` field is literally the (Base64-encoded) `Coverage` key of that seed, written once at bank-time. `seen?/2` never recomputes a stored entry's key on read; it only compares the raw bytes already on disk against a freshly computed key for the *candidate* being drawn right now. So enrichment does **not** corrupt or desync the corpus file — every existing record still decodes and replays correctly (`corpus_replay_test.exs`'s replay path never touches `key=`, and no test asserts an exact `Coverage.key_string` value, so nothing goes red) — but it **does** reset seed-dedup identity against history: pre-change records carry old-format (coarse) keys, so post-change `seen?` checks will no longer recognize a freshly-drawn candidate as "already banked" against those old entries once the key format changes shape. Expect a burst of re-banked seeds at the new, finer granularity immediately after the change lands, growing `seeds.sexp`. This is acceptable — `Antigen.Corpus`'s own moduledoc already establishes the store as "committed, never-pruned" by design, and re-banking under a refined key is the intended effect of the enrichment — but it is a real, one-time widening of what counts as "new", not a no-op.

## 3. Part 2 — Corpus-backed fillers (type-safe crossover)

The mutation/typed-term generators build terms with **typed holes** filled by fresh `Term.gen_term(ctx, goal)` draws. Crossover reuses *real banked terms* as those fillers.

**Mechanism:** a new `Antigen.Generators.SeedPool` that, at generation time, loads a corpus file once (default `test/antigen/seeds.sexp`), extracts every **closed** (empty-context, de-Bruijn-closed) `typed_term` sub-corpus term indexed by its **recorded type** (the seed's `payload.type`), and exposes `pool_term(goal) :: Gen.t() | :none` returning one banked term whose type is syntactically equal to `goal` (or `:none` if the pool has none).

`Term.gen_term(ctx, goal)` (and/or the mutation fillers `gnat`/`gvec0`/`gvec_sz`) gain a **low-frequency** branch: with small weight, if `SeedPool.pool_term(goal)` is available, draw a banked closed term instead of generating fresh. Closedness guarantees the spliced term is valid in any context (no shift needed); type-equality guarantees well-typedness at the hole.

**Determinism/safety:**
- The pool is sourced from `:typed_term` seeds **only** — never `:mutant_term`. A `:mutant_term`'s `payload.type` is `goal_of(fault)`, documented in `Antigen.Generators.Mutation` as "a nominal goal describing the fault site, never a proven property of the mutant" — its `payload.term` is *deliberately* ill-typed at that recorded type (that's the entire point of a mutant). Indexing the pool by that field would silently defeat Part 2's whole soundness argument (a "banked term of type T" would not actually check at T). `:typed_term` seeds are the only challenge kind whose `payload.type` is a genuine, kernel-checked type of `payload.term`.
- The pool is built from **closed** seeds only (drop any with a non-empty ctx or a free de-Bruijn index — reuse `Shrink.closed?`-style checking). This is what makes context-free splicing sound.
- Type match is **syntactic equality** of the goal type-term against the seed's stored `type` (no kernel call). Conservative but sound.
- If the pool file is absent/empty, the branch is inert (`:none`) — generation falls back to fresh, so the feature degrades gracefully and tests don't depend on a populated pool.
- **Quarantine:** `SeedPool` lives under `lib/antigen/generators/` and must contain **no** literal `StreamData` (grep-enforced by `architecture_test.exs`) — it uses `Antigen.Corpus` + the `Antigen.Gen` DSL only.

## 4. Part 3 — Health-adaptive biasing

`Runner.explore/1` today draws **all** `count` challenges up front (`draw(opts[:gen], count)`), then reduces and computes health post-hoc — so health can't feed back into generation.

**Change:** restructure `explore/1` to run in **rounds** (a fixed round size, e.g. 200 challenges), computing per-vertical health after each round and **re-weighting** the generator mix for the next round toward the vertical with the lowest health stamp (e.g. a vertical stamped `:vacuous` or with the lowest reduction_activity/diversity gets a higher draw weight). The mix is a weighting over `Mix.Tasks.Antigen.default_gen/0`'s 11 top-level `{weight, gen}` branches — a flat `Antigen.Gen.frequency/1` list (data, per `Gen`'s "reified, inspectable" contract), so the runner can pattern-match `{:frequency, ws}` and rebuild it with adjusted integer weights without touching `Cure.Core.*` or the generator internals. (Note: `Antigen.Generators.Term.default_gen/0` is a *different*, narrower 3-branch function — all three branches drive the same underlying `gen_term` distribution under different assay tags — and is not the mix this part reweights.)

**Vertical ↔ health-signal mapping — by challenge KIND, not by branch position:** `health_metrics/1` and `mutation_metrics/1` filter challenges by `kind` alone, not by which `default_gen` branch produced them — and two pairs of branches produce the *same* kind as each other: `Conversion.conv_accept/1` (branches 9–11) emits `kind: :typed_term`, exactly like `Term.typed_term/1` (branches 4–6); `Conversion.conv_reject/0` (branch 8) emits `kind: :mutant_term`, exactly like `Mutation.mutant/0` (branch 7) (verified: `Antigen.Generators.Mutation`'s own faults never set `witness: :conv`, so `conversion_stamp`'s reject-count cleanly isolates branch 8, but `mutation_stamp`'s `reason_diversity`/`survivors`/`max_depth`/`wrap_diversity` pool branches 7 *and* 8 together indiscriminately). So the three stamps do **not** align with three disjoint branch ranges; the branches only separate into three cleanly-disjoint **groups**:
  - **Group T** (branches 4–6, 9–11 — every `:typed_term`-emitting branch): feeds `health_stamp` (binder_usage/reduction_activity, pooled across all six) and also supplies whatever fraction of `conversion_stamp`'s `conv_accept_count` its output happens to hit the recognized carrier shape.
  - **Group M** (branches 7–8 — every `:mutant_term`-emitting branch): feeds `mutation_stamp` (pooled across both) and branch 8 alone supplies `conversion_stamp`'s `conv_reject_count`.
  - **Group F** (branches 1–3: `Totality`/`Positivity`/`Forcing`): no metric anywhere measures their output; fixed weight, never a reweight target (see §7 Non-goals).

  Reweighting therefore operates at **group** granularity, not per-branch: bump Group T's total weight when `health_stamp == :vacuous`, bump Group M's when `mutation_stamp == :vacuous`. `conversion_stamp`'s two *separate* counters (`conv_reject_count`, `conv_accept_count`) are precise enough to also motivate a group bump when one polarity is scarce (`conv_reject_count == 0` → bump Group M; `conv_accept_count == 0` → bump Group T) — but `conversion_stamp` cannot motivate reweighting *within* a group (e.g. "more branch 8, unchanged branch 7," or "more branches 9–11, unchanged branches 4–6"), since the metrics that would distinguish them don't exist. Finer-than-group reweighting is out of scope for this run.

**Correlating branch position to group:** `Gen.t()` (`lib/antigen/gen.ex`) carries no per-branch labels — `{:frequency, ws}` is just a list of `{weight, gen}` pairs, and `Antigen.Gen.tag/2`'s `{:tagged, ...}` variant is restricted to `:unsized | :size_monotonic`. Rather than extending `Gen.t()` with a new tag (which would pull `lib/antigen/gen.ex` into scope, beyond §6's Files list), the runner correlates **fixed positions** in `Mix.Tasks.Antigen.default_gen/0`'s literal 11-branch list to the three groups above (indices 1–3 = Group F, 4–6 and 9–11 = Group T, 7–8 = Group M), matching that function's already-committed branch order and its adjacent doc-comment. This is a real coupling: reordering or resizing `default_gen/0`'s branch list silently miscorrelates groups unless the position table is updated in lockstep — a guard test (§5) pins the branch count/order so a future edit to `default_gen/0` fails loudly instead of silently misdirecting the bias.

**Constraints:**
- **Behavior-preserving default:** with adaptivity disabled (a `bias: false` opt, default for the existing static tests) `explore/1` produces the *same* outcome as today (one batch, uniform mix) — concretely, `bias: false` must perform exactly **one** undivided `draw(opts[:gen], count)` call, not a round-loop with `round_size == count` or any other form of re-batched drawing. This is not a paraphrase-level detail: `Backend.StreamData.interp/1` + `Enum.take/2` is **not composable** — verified directly (`Antigen.Backend.StreamData.interp(gen) |> Enum.take(4)` called twice back-to-back does not concatenate to equal one `interp(gen) |> Enum.take(8)`, and is not even reproducible run-to-run within the same process). So if the round loop is written generically and merely invoked with round-count 1 for `bias: false`, that is fine *only if* it still issues a single `draw` call for the full `count` — any implementation that re-`interp`/re-`take`ues the same `gen` in chunks, even with unchanged weights, changes the drawn values and breaks this constraint.
- The round loop reuses the existing per-challenge reduce body (assay → bank/report) unchanged — only the *draw* is re-batched and re-weighted, and only when `bias: true`.
- Total challenge count and the final health/infection reporting are unchanged in shape.
- **`--bias` needs `count > round_size` to do anything:** `Mix.Tasks.Antigen`'s existing `@default_count` is 200, the same as this part's example round size. `mix antigen --bias` with no `--count` override runs exactly one round — health is computed once, after the only round, with no "next round" left to reweight — so it silently behaves like `bias: false`. `--bias` only has an observable effect when the caller also raises `--count` well above the round size (as §5 item 5's `--count 800 --bias` sanity check already does); worth a one-line note in `Mix.Tasks.Antigen`'s `--bias` docs so this isn't a silent no-op surprise.

## 5. Testing (TDD, per Stage 4)

1. **(Part 1)** `Coverage.key/1` distinguishes two terms that today collide — e.g. `λ.λ.x` vs `λ.(f x)` at equal depth/ctors/label produce **different** keys after enrichment (RED against current coarse key); the key remains bounded (a property test: N random terms yield ≤ K distinct keys for small K, proving it still plateaus). `key_string/1` round-trips the new fields.
2. **(Part 2)** `SeedPool.pool_term(goal)` returns a closed banked term of exactly `goal`'s type for a populated pool, `:none` for an absent/empty file; every returned term passes `Term.term?` and is closed. A dedicated test: a corpus file containing only `:mutant_term` records (no `:typed_term`) yields an empty pool / `:none` for every goal (RED against a naive implementation that pools any challenge kind with a `type`/`term` pair) — proves the exclusion in §3 is enforced, not just documented. A generator test: with the seed pool wired, some fraction of drawn fillers are banked terms (reachability), and every produced challenge still satisfies its construction guarantee (mutants still infer-reject; typed_terms still infer-accept).
3. **(Part 2)** Quarantine: `architecture_test.exs` stays green (no `StreamData` literal in `SeedPool`).
4. **(Part 3)** `explore(bias: false)` (default) is outcome-identical to today on a fixed challenge set; `explore(bias: true)` runs the round loop, and a test shows the next round's weight vector shifts toward **Group T** when `health_stamp` is made artificially `:vacuous` (branches 4–6 and 9–11 all rise together, not a subset) and toward **Group M** when `mutation_stamp` is made artificially `:vacuous` (branches 7–8 rise together). Floor weights hold (no branch drops to 0). A separate test asserts Group F's (`Totality`/`Positivity`/`Forcing`, branches 1–3) weights are unchanged across rounds under `bias: true` (no health signal exists for them, so they must never be a reweight target — only a fixed/floor contributor). A guard test asserts `Mix.Tasks.Antigen.default_gen/0` has exactly 11 branches in the documented order (RED if a future edit reorders/resizes the list without updating the position→group table this part relies on).
5. **Full suite once** (Stage 5) + a sanity `mix antigen --count 800 --bias` to a tmp corpus: health lines should show **improved** diversity/reduction_activity vs the pre-change baseline (record both).

## 6. Files

- **Modify:** `lib/antigen/coverage.ex` (enriched key + `key_string`), `lib/antigen/runner.ex` (round loop + biasing, opt-gated), `lib/antigen/generators/term.ex` (+ mutation fillers) for the corpus-backed branch, `lib/mix/tasks/antigen.ex` (`--bias` flag).
- **Create:** `lib/antigen/generators/seed_pool.ex`, tests under `test/antigen/`.
- **Untouched:** `Cure.Core.*` (TCB), the corpus format/migration, `Challenge`.

## 7. Non-goals (YAGNI)

- **Grey-box kernel-branch instrumentation** — true execution-trace coverage requires editing `Cure.Core.*` (TCB, HARD-STOP-review); explicitly deferred as a separate operator-reviewed run.
- Cross-context splicing of open terms (only closed banked terms are pooled — sound without a shift/typing engine in the generator).
- Kernel-call-based type matching for the pool (syntactic equality only).
- Changing the corpus on-disk format or re-banking committed corpora.
- Adding new health metrics for the `Totality`/`Positivity`/`Forcing` verticals (Group F, §4) so they can participate in adaptive reweighting — they keep a fixed weight this run; a future run may instrument them.
- Finer-than-group reweighting within Group T (per assay-id, branches 4–6 vs 9–11) or Group M (branch 7 vs 8) — the existing metrics don't distinguish sub-branch provenance (§4).

## 8. Risks

- **Enriched key stops plateauing** (unbounded key space → dedup never converges, health gate breaks). Mitigation: every new feature is bucketed to a small fixed cardinality; §5 item 1's plateau property test guards it.
- **Adaptive loop changes existing test outcomes.** Mitigation: `bias: false` default is behavior-preserving; only `mix antigen`/opt-in paths use rounds.
- **Corpus-backed filler contaminates a mutant** (a banked term isn't actually the claimed type). Mitigation: syntactic type-equality + closed-only + the construction-guarantee assertions in §5 item 2 (mutants must still infer-reject); if a banked term ever breaks that, it's caught red.
