# Value-Surface Wave 3 — `@extern` / FFI in the dependent pipeline

**Goal:** Let a bodyless `@extern(:mod, :fn, arity)` function declaration elaborate through the DEPENDENT pipeline (as a typed opaque postulate) and emit to a direct Erlang remote call — the FFI path to AtomVM's NIFs and OTP. No kernel CODE change (the extern's declared type is an asserted FFI axiom, not a kernel-proven fact — the standard postulate boundary; see §4's Claim A/B split).

**Status of the program:** Waves 1 (`pickup`) and 2 (`List`) landed on `autopilot/kernel-parity-batch` (unmerged). `@extern` is promoted ahead of lambda-inference on scout evidence (§0).

---

## 0. Why `@extern` is next (reorder rationale — decided from scout evidence)

The value-surface roadmap's original wave order put lambda-inference before `@extern`. A scout of both gaps (this session, dependent-pipeline-verified) reversed that for one decisive reason:

- **`@extern` is the *earlier* blocker in every one of the ~9 std modules that fail.** A bodyless `@extern` decl (e.g. `Std.List`'s `@extern(:erlang, :length, 1) fn length/1`) is at or near the top of each module and halts the whole-module body pass (`program.ex:760-766`, `Enum.reduce_while`/`{:halt, err}`) *before* any lambda body is ever reached. So **lambda-inference alone flips zero modules** — even `Std.List` needs `@extern` first. `@extern` alone plausibly flips ~2–4 modules (math, map firmly; pair, gen plausibly), and reduces the rest to two cheap literal-support follow-ons (atom-literals → system + test; string-literals + `<>` → io + string), leaving lambda-inference as the last mile for just `list`.
- **`@extern` is kernel-code-free and lambda-independent** (§4 Claim A; §5). It is confined to the elaborator (accept the bodyless decl) + emit (remote-call wrapper); disjoint from the motive/inference machinery lambda-inference touches. (It is NOT trust-free in the logical sense — the asserted FFI type is an axiom, per §4 Claim B — but that trust cost is orthogonal to this reorder rationale, which is about kernel/inference machinery, not the logical trust base.)

Revised remaining wave order: **`@extern` → atom-literals → string-literals+`<>` (the "String" wave) → lambda-inference (`list`) → Map/tuples/tail.** Atom-literals is flagged (§5) as the single highest-leverage follow-on (a ~1-clause addition to the literal handler that flips 2 modules) and should be the wave immediately after this one.

## 1. The gap (dependent-pipeline-verified)

The dependent pipeline has **zero** `@extern` handling today (`grep extern lib/cure/elab/` → nothing; the only `core/` hits are `to_external`/`from_external` false positives in `term.ex`). So this is net-new elaborator + emit code, not a tweak.

### 1.1 Surface shape

- `@extern(:mod, :fn, arity)` is a **decorator on a function decl**; the parser folds it into the function's `meta` as `[extern: {mod, fun, arity}]` (`lib/cure/compiler/parser.ex:4757-4774`, literal extraction `:4781-4800`, which includes the `defp extract_literal_value(other), do: other` catch-all at `:4800` for an AST shape none of the typed clauses recognize). If the decorator's arg count is not exactly 3 (`case args do [m, f, a] -> … ; _ -> args end`, `:4763-4766`), `extern_val` is left as the raw args list rather than a `{mod, fun, arity}` triple — a malformed `@extern(...)` is out of scope for this spec (every existing `lib/std/*.cure` decl passes exactly 3 args) but the plan should not assume the elaborator's `meta[:extern]` pattern-match on a 3-tuple is guaranteed to succeed for arbitrary future source. The node stays `{:function_def, meta, body}`.
- A bodyless `fn length(list: List(T)) -> Int` (no `=`) produces `body = []` — the "signature only" arm (`parser.ex:2398-2402`; the multi-clause arm `:2385-2395` also yields `[]` and additionally sets `meta[:clauses]`).

### 1.2 Exact failure site

`Declarations.elaborate/2` runs `register_signature` then `elaborate_function_body` (`lib/cure/elab/declarations.ex:26-29`):

- `register_signature` **succeeds** for an extern: it builds the Π from the signature and stores a placeholder def body `{:hole, "__pending__"}` (`declarations.ex:36-40`, via `function_signature/2` `:76-101`). **The type is fully derivable from the signature alone — no body needed.**
- `elaborate_function_body` calls `single_body([])` → fallthrough `single_body(expr), do: expr` (`declarations.ex:264-265`) → returns `[]` → `elaborate_body([], …)` → catch-all (`declarations.ex:383-387`) → `Elaborator.elaborate_expr_typed([], …)` → the catch-all `elaborate_expr_typed(other, …), do: {:error, {:unsupported_expression, other}}` at **`elaborator.ex:569`** with `other = []`.

Result: `{:unsupported_expression, []}`, halting the module at its first extern decl. (Line 569 is authoritative-current as of this revision — verified by re-grepping the clause; this file drifts, so the executor MUST re-verify the catch-all clause by identity, not line number, before relying on it.)

## 2. Design (decided)

`@extern` is a **typed opaque postulate with a runtime remote-call realization**: the declared Π is the trusted type (FFI signatures are always asserted, never proven), the kernel never unfolds it (bodyless globals are already opaque neutrals — §4), and emit gives it runtime meaning as a direct Erlang remote call. This is **sound-given-the-axiom** — there is no term to check, normalize, convert, or erase, so the kernel's internal consistency is preserved *conditional on* every asserted extern signature being honest (§4 draws the line precisely; do not read this as an unconditional soundness claim).

Two changes, both below the typing judgement's trust boundary in the sense that the kernel is untouched:

### 2.1 Elaborator: accept the bodyless extern (E-layer)

In `elaborate_function_body` (`declarations.ex:45-71`): when `meta[:extern]` is present, **skip body elaboration entirely** — do NOT call `elaborate_body`, `Kernel.check`, or `Relevance.check` (there is no term). Keep the Π already computed by `function_signature/2`, and **replace the `{:hole, "__pending__"}` placeholder with an extern MARKER** carrying `{mod, fun, arity}`.

**Marker representation (contract, exact form is a plan decision):** the def must be marked such that (1) body-elaboration / `Kernel.check` / `Relevance.check` are skipped, (2) `emit`'s `reject_holes` (`emit.ex:104-116`) does NOT see a hole (a pending `{:hole, …}` would be rejected — so the marker must NOT be a hole), (3) emit can route it to the remote-call wrapper, and (4) — verified below — `TotalityClosure.certify_type_level` does not crash or spuriously reject the module if the extern's name is ever pulled into the type-level closure. A dedicated `def` field (`extern: {mod, fun, arity}`) or a `body: {:extern, {mod, fun, arity}}` sentinel both satisfy (1)–(3); the plan picks one and pins it with the "typechecks AND ships" test (§3 antibody 2).

**Contract point (4) — the TotalityClosure consumer (verified against source, not merely assumed):** elaboration-time skipping of `Kernel.check`/`Relevance.check` (point 1) is NOT the only place a def's body can reach the kernel checker. `Program.check_ast_elixir_core/1` unconditionally runs `TotalityClosure.certify_type_level(env)` after the whole module's body pass (`program.ex:137`, and again at `:517`, `:633`), on the FULL env (not just this module's own defs — a shared env can pull in another module's families too). `type_level_fns/1` (`totality_closure.ex:22-27`) walks every inductive family's/constructor's parameter and index telescopes (`seed_globals/1`, `:49-59`) and transitively every `:global` name reachable from there (`close/3`, `:64-75`, via `collect/1`, `:79-92`), then `certify_type_level/1` (`:34-45`) resubmits each such name to `Kernel.validate_certificate/2` (`kernel.ex:369-385`). **If an extern function's name is ever referenced from a dependent-index position** (e.g. a future length-indexed `Vector` computing its index via an extern `length`), it lands in this closure regardless of what happened at declaration time.

`Kernel.validate_certificate/2` on a non-`builtin_op` def falls to its generic branch (`kernel.ex:376-383`), which calls `check_def/2` (`:308-330`). `check_def/2` has exactly two clauses: a `%{builtin_op: op, type: type_term} when not is_nil(op)` clause (`:319-320`) that checks ONLY the declared type and explicitly never touches the (absent) body — its own comment names this precise scenario ("Reachable via `TotalityClosure.certify_type_level` once builtin-op spines occur in TYPE positions") — and a generic `%{type: type_term, body: body_term}` clause (`:322-329`) that calls `check(ctx, body_term, Eval.eval(type_term, []))` on whatever `body_term` is. `Env.add_def/4-5` (`inductive.ex:33,41`) always leaves `builtin_op: nil` unless a def is separately tagged via `Env.register_builtin_op/3` (`inductive.ex:97-99`) — a call the extern-elaboration branch does not make unless the plan says so. **So an extern marker that is only a body/def-field sentinel (not builtin_op-tagged) will, if ever reached by `TotalityClosure`, be handed to `Kernel.check/3` as if it were a real Core term** — an outcome the kernel-checker was never designed to accept and that this spec's "no term to check" claim (§2, opening paragraph) would then be false for.

This is dormant for the wave's predicted-flip modules today — `Std.Math`/`Std.Map`/`Std.Pair`/`Std.Gen` declare no inductive families whose telescopes reference their own externs, so `seed_globals` never seeds them (verified: `grep @extern lib/std/{math,map,pair,gen}.cure` shows only leaf arithmetic/map/pair/rand externs, none referenced by any family index in those or other currently-loaded modules). But dormant-today is not the same as designed-safe, and the spec's job is to fix the design, not just this wave's fixture set.

Reusing `builtin_op` as the marker's carrier field (the naive fix that suggests itself, since `check_def` already special-cases it) is **NOT actually safe** — `builtin_op` is overloaded with three OTHER consumers that all assume the op value is a stable arithmetic/comparison atom (`:add`, `:lt`, …), not an extern triple: the Normalise compute hook (arithmetic delta-fold), `Env.builtin_op/2` read at emit's own call-site lowering (`emit.ex:354-365`, which for any `{:global, name}` value-position reference dispatches to `builtin_op_wrapper(op)` and thence `erl_binop(op)` — a function with no clause for a `{mod, fun, arity}` triple), and GuardLint's Z3 translation. Tagging an extern this way would silently miscompile (or crash) the FIRST time an extern function is referenced as a first-class value rather than called saturated — a real, if narrower, regression surface.

**Resolution (adopt into the plan, E-layer only): do not let `TotalityClosure` attempt to certify an extern-marked global at all.** Certification is inherently the wrong operation for an extern — an FFI declaration has no Core body to δ-reduce to even if "certified" (§2's own framing: the Π is asserted, never proven), so requesting `Kernel.validate_certificate` for one is a category error, not a corner case to survive. The fix belongs in `lib/cure/elab/totality_closure.ex` (untrusted E-layer, already in scope for this wave). The correct edit site is **`certify_type_level/1` (`:34-45`)**, not `close/3`: `close/3` (`:64-75`) only discovers *transitively*-reached names and never decides whether the name it was called with is itself certification-worthy — a name reached directly as a **seed** (`seed_globals/1`, `:49-59`, called straight from `type_level_fns/1`, `:22-27`, whose initial `acc` already equals `seeds`) never passes through `close/3`'s `Env.get_def` branch as an entrant at all, so a filter placed inside `close/3` would miss the direct-seed case. `certify_type_level/1` is the single choke point every member of `type_level_fns(env)`'s result (seeded AND transitive alike) passes through before `Kernel.validate_certificate/2` is called — filter extern-marked names out of that list (or `:cont`-skip them inside the `Enum.reduce_while`) there, uniformly. This requires **zero change to `lib/cure/core/kernel.ex`**, keeping §4's "kernel untouched" and §5's "`core/` diff EMPTY" claims true, and keeps every existing `builtin_op` consumer's assumption (op-atom-shaped value) intact. Add this as an explicit sub-step of §2.1 in the plan, and add antibody 7 below to pin it.

### 2.2 Emit: lower to the remote call (C-layer, mirrors classic — does NOT call it)

Emit must recognize the extern marker and produce the wrapper form, MIRRORING (not calling) the classic oracle `codegen.ex:691-705`:

```elixir
remote_call =
  {:call, line, {:remote, line, {:atom, line, ext_mod}, {:atom, line, ext_fun}}, param_forms}
clause = {:clause, line, param_forms, [], [remote_call]}
{:function, line, fn_atom, arity, [clause]}
```

i.e. a wrapper `fn_atom/arity` whose single clause binds params `V0…Vn-1` and issues `mod:fun(V0, …, Vn-1)`. The `V<pos>` naming convention already exists (`peel_params/4`, `emit.ex:141-150`) and `present_arity/2` (`emit.ex:367-372`) already computes an arity from a def's `quantities` — reuse both as **precedent for the convention and the arity count**, not as literally-callable machinery: `peel_params/4` peels an actual `{:lam, dom, body}` chain (`:145-148`), which a bodyless extern does not have (there is no term to peel — §2, opening paragraph), so calling it on the extern's marker would hit its no-op catch-all (`:150`) after zero iterations and silently produce an empty param list for any arity > 0. The new remote-call emitter must instead synthesize `param_forms` directly from the arity (`Enum.map(0..(arity - 1), &{:var, @line, :"V#{&1}"})` or equivalent) — mirroring the classic oracle's own `build_param_forms/3` (`codegen.ex:698`), which likewise builds params from the surface arity, not by peeling a term.

The **"emit.ex:60 filter widen"**: line 60 is `names = for {name, d} <- defs, is_nil(Map.get(d, :builtin_op)), do: name` (`emit.ex:55-63`) — it already skips body-less `:builtin_op` defs because `function_form` would crash on their nil Core body. Widen twofold: (1) the all-defs path must ALSO skip / specially-route extern-marked defs (same nil-body shape); (2) the live `/3` path (explicit `local_defs`, `emit.ex:71-80`) must route extern-marked names to the remote-call emitter instead of the generic `function_form` (`emit.ex:125-139`, which reads `%{body: body}` + `Erase.erase` and would misbehave on a bodyless extern). No classic module is called — the form is duplicated, so the firewall stays green.

### 2.3 What must NOT change

- The kernel proper — `lib/cure/core/{eval,normalise,conv,quote,kernel,term,erase,inductive}.ex` — stays EMPTY of changes (§4). `builtins.ex` need not change either this wave.
- No new Core term type. The extern marker lives in the E-layer def/emit only; the kernel sees only the already-opaque global.
- `declarations.ex`'s dispatch whitelist for real bodies is untouched (extern is handled by an EARLIER `meta[:extern]` branch in `elaborate_function_body`, before the body dispatch, not by adding a node to the whitelist).

## 4. TCB / kernel: untouched, in the code sense — NOT trust-free, in the axiom sense

Two separate claims are easy to conflate here; this spec makes only the first one, and must not be read as making the second.

**Claim A — kernel-code-free (TRUE, this is what "TCB untouched" means in this spec).** The kernel already treats every `:global` head as an opaque neutral `{:nglobal, name}` unless it is totality-certified; δ-unfolding is gated on certification (`eval.ex:11-12, 41,49`; `conv.ex:10-18, 118`; uncertified globals compared by-name only, `conv.ex:153`). A bodyless `@extern` def has **no Core body to certify**, so it stays opaque — indistinguishable to the kernel from any uncertified postulate. It is never evaluated, normalized, converted-by-unfolding, quoted, or erased-as-a-term. Therefore **no change to `eval/normalise/conv/quote/kernel/term/erase/inductive`.** The `git diff` gate (§5) enforces this: `core/` must be EMPTY of changes this wave (unlike Wave 2, `builtins.ex` is not touched either). This guarantee is not free-standing, though — it depends on nothing ever *asking* the kernel to certify an extern def in the first place (§2.1 point 4): `TotalityClosure.certify_type_level` is the one whole-program pass that could, so `lib/cure/elab/totality_closure.ex` must skip extern-marked globals rather than submit them to `Kernel.validate_certificate`. That fix is E-layer (untrusted), not kernel, and is included in the diff scope below.

**Claim B — logical trust base (NOT free; `@extern` genuinely widens it).** The declared Π for an extern is an **asserted axiom**, taken on faith: the checker cannot inspect `:erlang.length`'s actual behavior to confirm it really is `List(a) -> Int`. This is the standard, accepted FFI-postulate boundary every dependent language draws — Idris `%foreign`, Agda `postulate` + `COMPILE`, Coq `Axiom`/extraction — and this design is not claiming to do better. The failure mode is not merely "a wrong signature crashes at runtime" (which would at least be loud); a wrong signature that happens to *run without crashing* is **silent unsoundness**. Example: `@extern(:erlang, :phash2, 1) fn bad(x: Int) -> Void` type-checks under this design (the Π is asserted, not proven), never crashes (`:erlang.phash2/1` always returns an integer), and hands the program an inhabitant of the empty type — from which anything is derivable. No kernel code is wrong; the *axiom* is wrong, and the kernel has no way to know that, by design (this is Claim A holding, not failing).

**Why this is acceptable, not a wave-3 defect to fix:** the machinery (elaborator + emit, this spec's actual deliverable) is trustworthy and auditable — every `@extern` is a single greppable line, and its asserted type is checkable by a human against the target BIF's real signature (Erlang/OTP docs). The kernel stays internally consistent *given* the axioms it's handed, which is the only thing a kernel can promise about postulates it cannot itself execute. Nothing in this wave should describe `@extern` as "TCB-free" or "sound by construction" without this qualification — those phrases, unqualified, overclaim. Where this spec uses "TCB-free" elsewhere (§0, §1), read it as Claim A only.

## 7. Out of scope (do NOT build here)

- **Atom literals** (the next wave — flips system + test; ~1-clause add to the literal handler at `elaborator.ex:446`).
- **String literals + `<>`** (the "String" wave — flips io + string).

- `@extern` with a **non-trivial body** or clause guards, effect typing of FFI, or any dependently-typed refinement of the FFI signature (the Π is taken as an asserted postulate — that is the whole design).

- Adding externs to `@auto_prelude`.
