## 1. Part A — fields-only constructor values (ledger #28)

**Audit facts this rests on (verified 2026-07-09, do not re-derive):** the kernel is ALREADY fields-only at every load-bearing site — ι binds `reverse(args) ++ env` with branch arity == field count enforced at type-check time (eval.ex:56-62, kernel.ex:708, reference value kernel.ex:729 is fields-only); erase drops grade-0 params (erase.ex:24-28); emit's BEAM tuples are tag+fields (emit.ex:179). Conversion's vctor comparisons (conv.ex:88-89 via length-strict conv_spine? :109-112; same_value_no_delta? :172-180) are safe under the **shared-type conversion invariant**: Conv is entered only on same-type pairs (kernel.ex:215, :261, :1070; meta_check.ex:20; elaborator.ex:3391, :3473; elab/unify.ex:321 — closed, meta-free), and a vctor comparison is reached only after the enclosing `{:vdata, family, params++indices}` already converted (conv.ex:85-86). Mixed spelling can only false-REJECT (length gates conv.ex:110, elab/unify.ex:341), never false-accept. The ONLY params-on-spine producer is the K6 ctor TERM form (kernel.ex:153-160 infer, :274-275 check→check_via_infer; added for Eq bridge_step, kernel.ex:144-151 comment), which yields a `{:vdata}` TYPE in inference — but nothing structurally prevents such a term from being evaluated and eliminated.

**Canonical spelling: fields-only.** Changes:

1. **A1 — ι-rule coercion (closes the K6 hazard).** At every ι site — eval.ex:56-62, normalise.ex:235-246, normalise.ex:269-288 — the branch tuple carries its declared `arity`; when `length(args) > arity`, bind only the LAST `arity` args (`Enum.drop(args, length(args) - arity)`): params precede fields on a K6 spine, so dropping the leading extras coerces to fields-only exactly. `length(args) == arity` binds as today (zero-cost on the canonical path). `length(args) < arity` is impossible for kernel-checked terms — leave behavior as today (no new error path; the kernel's type-check-time guard kernel.ex:708 owns that invariant).
2. **A2 — conversion mixed-spelling completeness.** In `conv_spine?`'s callers for vctor pairs (conv.ex:88-89) and `same_spine_no_delta?` (conv.ex:177-180): when lengths differ AND the signature resolves the ctor's field count F, coerce each side longer than F to its last F elements before the pairwise walk; if the signature cannot resolve the ctor, keep today's strict-reject. Sound by the shared-type invariant (dropped positions are type-determined); turns the false-reject into agreement, changes NO accept into reject.
   - **Signature threading (verified gap, not yet implemented):** today the `same_neutral_no_delta?`/`same_value_no_delta?`/`same_spine_no_delta?` family (conv.ex:152-180) is 3-arg — `(x, y, depth)` — with NO `sig` parameter; only `conv_spine?` (conv.ex:109-112, reached via `conv_struct?`) already carries `sig`. `conv_val?` (conv.ex:59-66) receives `sig` as its 4th argument and calls `same_neutral_no_delta?(n1, n2, depth)` — sig is in scope at the call site but not forwarded. A2 for the `same_*_no_delta?` path therefore requires adding a `sig` parameter through this whole family (`same_neutral_no_delta?/4`, `same_value_no_delta?/4`, `same_spine_no_delta?/4`) and threading it from `conv_val?`'s existing (already-in-scope) `sig` argument at its `same_neutral_no_delta?(n1, n2, depth)` call site (conv.ex:60). This is a same-file (conv.ex), signature-only-widening change — no new external input.
   - **Where the F-lookup/coercion itself must live (implementability note):** `conv_spine?` and `same_spine_no_delta?` are SHARED, ctor-name-blind helpers — each is called from both the `:vdata` clause (conv.ex:85-86, :169-170; params++indices, no ctor field-count concept applies there) and the `:vctor` clause (conv.ex:88-89, :172-173) of its caller, and in both cases the caller checks `n1 == n2` (the ctor/family name) but does NOT pass it into the shared walker. The spec's own wording — "`conv_spine?`'s **callers** for vctor pairs" (conv.ex:88-89) and, by the same structure, `same_spine_no_delta?`'s caller (`same_value_no_delta?`'s `:vctor` clause, conv.ex:172-173) — already correctly locates the F-lookup/coercion in the CALLER, which has `n1`/`n2` in scope, rather than inside `conv_spine?`/`same_spine_no_delta?` themselves. Concretely: the `:vctor` clauses at conv.ex:88-89 and :172-173 look up F via `Inductive.get_ctor(sig, n1)`, coerce `vs1`/`vs2` (resp. `args1`/`args2`) to their last F elements when longer, THEN call the existing, unmodified `conv_spine?`/`same_spine_no_delta?` on the (possibly-coerced) lists — the shared helpers' own signatures do not need a ctor-name parameter, only (per the bullet above) the `sig` needed to perform the lookup. Do NOT thread a ctor-name parameter into `conv_spine?`/`same_spine_no_delta?` — that would incorrectly entangle the `:vdata` call path, which must NOT be coerced by this batch (Part A is constructor VALUES only; family param/index spelling is Part B's concern).
3. **A3 — K6 term form UNCHANGED as a typing rule.** Inference of params-on-spine ctor terms stays (kernel.ex:153-160, :274-275); its values are now coerced at elimination (A1) and tolerated at conversion (A2). No elaborator change.
4. **A4 — antibodies** (new `test/antigen/ctor_spelling_antibody_test.exs`): (i) a case-elimination of a params-on-spine ctor term evaluates to the SAME result as its fields-only spelling (the de Bruijn misalignment repro — must FAIL red before A1); (ii) `Conv` equates the two spellings of one ctor value under a shared type (red before A2); (iii) nf/eval never bind more args than branch arity (property over the Antigen ctor generators, or a directed test if the generator hookup is disproportionate — executor judgment, ledgered).

## 2. Part B — signature-aware nf readback (nf_ill_typed class)

**Facts:** `Normalise.nf`/`whnf` read back via 2-arg signature-less `Quote.reify` (normalise.ex:31, :42), collapsing an indexed family's param/index split — `Equivalent` (1 param + 2 indices) reads back `{:data, :Equivalent, [Nat, Z, Z], []}`, which fails re-inference `:arg_arity`. The kernel already reifies WITH `Context.signature(ctx)` where it matters internally (kernel.ex:626-627) and documents the collapse (kernel.ex:647-650). Two real Antigen campaigns: every `Equivalent` infection is `nf_ill_typed` (389/389, 202/202), zero `not_idempotent`. Both `nf_ill_typed` violations are raised by `lib/antigen/assays/term.ex`'s `term/subject_reduction` (line 73) and `term/normalization` (line 84) clauses, both of which call `Normalise.nf/3` directly — i.e. exactly the B1 target.

**Verified: normalise.ex has FOUR 2-arg reify/quote call sites, not two.** Besides `:31` (`whnf/3`) and `:42` (`nf/3`), the same file also has `:48` — the PUBLIC `Normalise.quote/3` (`def quote(value, depth, _opts \\ []), do: Quote.reify(value, depth)`, the 3rd param currently discarded) — and `:177` — `quote_nf/4`, used internally by `nf_struct`'s `:vpi`/`:vlam` clauses (normalise.ex:142-154) to reify a binder body at `depth+1`; `quote_nf` already RECEIVES `sig` as a parameter but drops it before calling `Quote.reify(depth)`. Both are load-bearing and must be included or B1 is incomplete: (a) without fixing `:177`, an indexed-family value nested under a Π/λ binder stays flat even after `:31`/`:42` are fixed, because `nf_struct` reifies binder bodies via `quote_nf`, not directly via `whnf`/`nf`'s own top-level reify call; (b) without fixing `:48`, the PUBLIC `Normalise.quote/3` — used across `lib/antigen/{assays/term.ex:48, generators/term.ex:94,356,400,430, generators/sig_menu.ex:312,336}` and `lib/antigen/assays/kernel_law.ex:100-101,179-180`, plus `test/antigen/generators/{equality,type_former,dep_match,primitive}_test.exs` and `test/antigen/generators/beta_subst_test.exs` — stays flat, which directly breaks B3 (see below).

Changes:

1. **B1** — normalise.ex:31, :42, :48, and :177: reify/quote with the context's signature (same form kernel.ex:626-627 uses), so `{:vdata}` readback splits params/indices per the family record everywhere within `Normalise`. For `:48`, repurpose the currently-unused 3rd parameter: `def quote(value, depth, sig \\ nil), do: Quote.reify(value, depth, sig)` — every existing 2-arg caller (all of the call sites enumerated above pass only `(value, depth)`) is unaffected (still defaults to flat `nil`); only a caller that explicitly starts passing a 3rd argument opts into the split. For `:177`, forward the closure's `sig` param into the trailing `Quote.reify(depth)` call: `Quote.reify(depth, sig)`.
2. **B2 — consumer audit (BEFORE B1 lands).** Scope note: `Quote.reify/3` itself is NOT modified by this batch (it is already signature-aware; its `nil`-default stays flat) — so a DIRECT 2-arg `Quote.reify(...)` call that never routes through `Normalise` is axiomatically unaffected and does not need auditing (e.g. `elaborator.ex`'s ~20 direct reify calls for elaboration diagnostics, and `test/cure/core/{quote,float_prim,int_prim,conformance}_test.exs`'s direct reify assertions — spot-checked 2026-07-09, none go through `Normalise`). The real audit surface is: every `Normalise.nf`/`whnf`/`quote` call site whose OUTPUT is consumed as a `:data`-shaped TERM (not immediately re-`Eval.eval`'d back to a value — see the "unaffected" bullet below). Known sites (grepped 2026-07-09, re-verify before executing — do not rediscover from scratch):
   - **Reconciled by widened B1** (normalise.ex `:31`, `:42`, `:48`, `:177` themselves).
   - **Unaffected — round-trips through `Eval.eval` before further use**, so flat-vs-split is invisible: `Eval.eval({:data, name, params, indices}, env)` (eval.ex:35-36) always concatenates `params ++ indices` into one flat VALUE arg list regardless of how the TERM was split, so any call site that reifies then immediately re-`Eval.eval`s never observes the split. This covers kernel.ex:975 (`specialize_branch_context`), kernel.ex:987 (`specialize_branch_value`), kernel.ex:86 (`Pi` codomain reify, consumed only as a closure body re-`eval`'d later), and kernel.ex:296 (both `Quote.reify` calls feed only a diagnostic `{:conversion_failure, ...}` tuple, never re-parsed as a `:data` shape). `elab/unify.ex:482` is already 3-arg (`Cure.Core.Quote.reify(depth, sig)`) — already signature-aware, no change needed.
   - **Documented flat-by-design, out of scope (§5)**: kernel.ex's `unify_indices` term diet — the `:data`-heads clause and its "Quote.reify always emits an empty `indices` list" comment are at kernel.ex:831-835 (not :828-831 — 828-829 is the preceding, unrelated `:ctor` clause). §5 already excludes "flat-vs-split at kernel.ex:828-831 [→ 831-835] index unification beyond what B2 proves necessary" — no change planned here; B2 only needs to confirm nothing upstream now feeds it split-shaped index terms it can't handle (it already handles `:data` terms with populated `is`/`is2`, so a split-shaped input is not obviously unsafe, but this is exactly the kind of claim B2's per-site table must state explicitly rather than assume).
   - **REQUIRES reconciling — confirmed regression, not hypothetical:** `test/antigen/generators/equality_test.exs:20` — `assert Normalise.quote(inferred, Context.length(cx)) == c.payload.type` — is a SYNTACTIC `==`, unlike `lib/antigen/assays/term.ex`'s `term/infer_check` (line 46-59), which compares via `Conv.conv_within?` (semantic; immune to flat/split because `Eval.eval` re-flattens both sides identically before `Conv` ever compares them — see the "unaffected" bullet above). Once B1 widens `Normalise.quote/3` (per the change above) AND `equality_test.exs:20` is updated to pass `Context.signature(cx)` as `Normalise.quote`'s 3rd argument, this reconciles cleanly — but the update to `equality_test.exs:20` is an edit to an EXISTING, currently-passing test, so it must be entered in the §3.4 flip ledger explicitly (see below); the §3.4 "grep for `{:data, _, _, []}`" heuristic will NOT surface it, because the flat shape here is produced at runtime by `Normalise.quote`, not pinned as a literal tuple in the test file. `type_former_test.exs`, `dep_match_test.exs`, `primitive_test.exs`, `beta_subst_test.exs` use the identical `Normalise.quote(inferred, depth) == c.payload.type` idiom but their generators are untouched by this batch (only `equality.ex` is in scope, per §0) and `Normalise.quote/3`'s widened default stays flat when called 2-arg — so those four are unaffected as long as their existing 2-arg call sites are left alone. B1 lands only after this table is written into the execution report.
3. **B3** — `lib/antigen/generators/equality.ex:80-83, :130-133` AND `test/antigen/generators/equality_test.exs:20` (ledgered under §3.4, see above): the deliberately-flat claimed type shapes ("reify has no signature to split it") update to the split shape, and the test's `Normalise.quote` call gains the `Context.signature(cx)` argument, in the SAME commit as B1. B3 is unsound without the `equality_test.exs:20` companion edit — landing the generator-side flip alone breaks that test (flat actual vs split claimed, syntactic `==`).
4. **B4 — antibodies** (new `test/antigen/nf_welltyped_antibody_test.exs`): (i) for an indexed-family term (the `Equivalent(Dec, Causal, Causal)` shape from the banked seeds), `check(nf(t), inferred_type)` succeeds — RED before B1 with `:arg_arity`; (ii) `nf(nf(t)) == nf(t)` on the same shapes (idempotence retained); (iii) the SAME indexed-family shape nested under a binder (e.g. `nf(ctx, {:lam, ty, equivalent_term})` or a Π codomain referencing it) — `check(nf(t), inferred_type)` succeeds, RED before the `:177` (`quote_nf`) piece of the widened B1 lands. (i)/(ii) alone exercise only `nf`'s own top-level reify call (`:42`); `nf_struct`'s `:vpi`/`:vlam` clauses reify binder bodies via `quote_nf`, a DIFFERENT code path (normalise.ex:142-154 → :177) that (i)/(ii) never reach, so (iii) is required for red-green coverage of that part of B1 — without it, the `quote_nf` fix lands with zero antibody proof.
5. **B5** — do NOT run open-ended `mix antigen` campaigns as a gate (they append banked seeds to committed corpus files); the antibodies + existing suite are the gate. If a spot campaign is run for evidence, `git checkout -- test/antigen/*.sexp` afterward and say so.
