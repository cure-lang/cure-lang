# Cure: A Technical Assessment

**A dependently-typed language for the BEAM — architecture, strengths, weaknesses, and a path forward**

---

## 1. What Cure Is

Cure is a dependently-typed programming language that compiles `.cure` source to standard BEAM bytecode, targeting the same VM as Erlang and Elixir. It is currently at **v0.34.3**, roughly 34 releases into a project that began as an Erlang implementation (v0.10) and was fully rewritten in Elixir (v0.12).

The scale is substantial and I verified it directly:

| Component | Size |
|---|---|
| Elixir compiler source (`lib/**/*.ex`) | **163,336 LOC** across 374 files |
| Self-hosted standard library (`lib/std/**/*.cure`) | **25,323 LOC** across 80 modules (~1,300 functions) |
| Test suite (`test/**/*.exs`) | **122,713 LOC** across 1,012 files (~6,350 tests) |
| Documentation (`docs/*.md`) | **15,543 LOC** across 43 files |
| Examples | 40 standalone `.cure` files + 11 full projects |

The largest single files are `lib/cure/elab/elaborator.ex` (**16,249 lines, 1,142 defs**) and `lib/cure/compiler/parser.ex` (**15,296 lines, 903 defs**).

### The pitch

Cure's stated thesis is the fusion of two worlds that rarely meet:

1. **Proof-assistant-grade type theory** — dependent functions (Π), dependent pairs (Σ), indexed inductive families (GADTs), cumulative universes, quantitative usage grades `{0, 1, ω}`, propositional equality, and size-change totality certification.
2. **First-class OTP concurrency** — FSMs, actors, supervisors, and applications, delivered not as compiler special-cases but as *transparent standard-library macros* that expand into ordinary checked Cure code over `gen_statem`/`gen_server`/`Supervisor`/`:application`.

The whole system runs through **one kernel-checked pipeline**: lex → parse (MetaAST) → dependent elaboration → trusted Core validation → quantitative erasure → BEAM emission. There is no unchecked "classic" path (it was deleted in v0.34).

## 2. Architecture Assessment

### 2.1 The trusted kernel — genuinely well-built

The kernel (`lib/cure/core/`, ~9,200 LOC) is the strongest part of the codebase. It is exactly what a TCB should be: small, pure, deterministic, and it **re-derives everything** rather than trusting the elaborator.

I verified the kernel's soundness properties empirically, not just by reading docs:

**Indexed-family type checking works correctly.** This program is properly rejected:

```cure
fn bad_append({a: Type}, xs: Vector(a, S(Z)), ys: Vector(a, S(Z))) -> Vector(a, S(Z)) =
  append(xs, ys)
```
```
-- CALL RESULT HAS THE WRONG TYPE [E093] --
Expected: Vector(?2, S(Z))
Found:    Vector(?2, plus S(Z) S(Z))
```

**Strict positivity is enforced** (rejecting `type Bad = MkBad(Bad -> Int)` with `E103`), **exhaustiveness is enforced** (`E118`), and the diagnostics are precise, source-anchored, and actionable — among the best I've seen in any compiler.

The kernel's design choices are sophisticated and correct:
- **de Bruijn indices** (no capture bugs, no alpha-equivalence court).
- **NbE definitional equality** (`eval.ex`/`conv.ex`) with **δ-reduction gated behind totality certificates** — the crucial safety property preventing the type checker from looping.
- **First-order index unification** with the full Solution/Injectivity/Deletion/Clash/Cycle rule set (`kernel.ex`), ported faithfully from Agda/Idris.
- **Nested strict positivity** (descends through wrapper datatypes).
- **Size-change termination** (Lee–Jones–Ben-Amram, ported from Idris) covering mutual recursion.
- **Serializable Core terms** enabling proof-carrying artifacts (`cure verify`).

The `@doc` comments throughout the kernel reference specific design specs, Idris source files, and Lean kernel functions — this is disciplined, literate engineering.

### 2.2 The standard library — ambitious and largely real

The stdlib is genuinely self-hosted and the dependent claims largely hold up. `lib/std/vector.cure` is a real length-indexed family with correct `append : Vector(a,m) → Vector(a,n) → Vector(a, plus(m,n))`, `take`/`drop` using Idris-style `with` convoys, and `from_list` returning a `Sigma`. The proof modules (`lib/std/proof.cure` and friends) contain **real kernel-checked proofs** — `plus_comm` is proved by induction and closed with `reflexive`/`rewrite`, not stubbed with `:cure_refl` atoms as in earlier versions.

The `Std.Proof.LinearArithmetic` module implements **executable Farkas witnesses** for verified linear-arithmetic reflection — 199 lines of genuine proof engineering. The certified regex engine (`lib/std_deps/regex/`, **13,415 LOC**) compiles regexes to indexed pattern machines with proof-carrying refutations.

There are **9 proof modules** and a `Std.Equivalent` inductive identity type with kernel-recognised `reflexive`.

### 2.3 The macro system — the architectural keystone

The decision to implement *all* OTP concurrency as transparent macros (`docs/MACROS.md`) is the most interesting architectural bet in the project. `fsm`, `actor`, `sup`, `app`, and the `beam_ops` vocabulary are ordinary `lib/std/*.cure` macros built on a staged, hygienic, self-proving macro facility (`syntax … becomes`, `computed by`, `syntax family`, `Std.Syntax` reflection, `quote`/splicing). This keeps the compiler surface small and means user libraries have exactly the same power as the stdlib.

The self-proving contract (`example … expands …`, exhaustive `explain` blocks) is a genuinely novel safety mechanism for macros.

### 2.4 Tooling — unusually rich

The CLI exposes ~40 subcommands: `compile`, `run`, `check`, `lsp`, `doc`, `fmt`, `migrate`, `repl`, `watch`, `test`, `bench`, `doctor`, `fix`, `publish`, `search`, `release`, `trace`, `john`, plus `verify`, `snap`, `story`, `export-types`, `replay`, `bless`, `synth`, `top`, `draw`, `audit`, `oracle`. There are editor integrations for VS Code, Neovim, and Zed, a highlight.js grammar, a LiveView playground, and an LSP server with hover/completion/definition/rename/semantic-tokens/inlay-hints/code-actions.

The **Antigen** engine (`lib/antigen/`) is a property-based *metatheory* fuzzer that generates random Core terms and checks kernel invariants (subject reduction, progress, conversion reflexivity, capture-avoiding β). There is also a **differential oracle** harness (`test/oracle/`) pinning ~30 dependent-typing scenarios at parity with Idris. This is research-grade verification infrastructure.

## 3. Strengths (What Cure Does Genuinely Well)

1. **A real, working dependent type checker.** I proved this by writing programs the checker correctly accepts and rejects. Indexed families, dependent motives, impossible-branch discharge, and definitional equality by computation all work.

2. **A clean, auditable trust boundary.** The kernel is small, pure, and re-checks everything. Z3 is explicitly *never* trusted (lint-only). The `cure audit trust` command inventories every axiom. This is the right architecture and it is actually implemented.

3. **Excellent diagnostics.** 106 structured diagnostic codes with authored source ranges, related spans, machine-safe fixes, "did you mean?" suggestions, and terminal/JSON/LSP projections. The `E093`/`E103`/`E118` output above is exemplary.

4. **Genuine OTP integration.** The `Std.Otp` typed process algebra (`Pid(m)`, `GenServer(q,r)`, linear `ReplyOf`, typed monitors, `Subject`, `Selector`, `Name`) is a serious piece of type-driven design — reframing BEAM processes as a typed algebra with linear reply capabilities.

5. **Comprehensive, honest documentation.** 43 documents including normative specifications (`MATCH.md` 1,707 lines, `PICKUP.md` 1,438 lines), a telescope-sorted glossary with an enforcing script, and an unusually candid launch checklist that records real bugs.

6. **Extraordinary test discipline.** 6,354 tests, warnings-as-errors, a metatheory fuzzer, and an Idris differential oracle. Only **2 TODO/FIXME markers** exist in the entire `lib/` tree.

7. **The onboarding path works.** I verified `cure new` → `cure run` → `cure test` end-to-end, and `cure check`/`cure compile` on real dependent programs.

## 4. Weaknesses (Verified Problems)

These are not speculation — each was reproduced against the current tree.

### 4.1 🔴 Macro containers break `cure check` and project-mode compilation

This is the most serious usability defect. **Every** macro container (`fsm`, `actor`, `sup`, `app`) fails `cure check`:

```
$ cure check lib/fsm.cure
-- COMPUTED MACRO EXPANSION FAILED [E092] --
The `fsm` computed macro could not produce valid Cure syntax: the generated
expansion was rejected by the compiler
```

I reproduced this against the **officially scaffolded `cure new --fsm` template**, the `cure_colony` showcase, and hand-written files. Worse, **in project mode** (any directory with a `Cure.toml`), the same files fail *compilation* with an opaque error:

```
$ cure compile lib/
-- COULD NOT READ FILE [E095] --
Cannot read `lib/machine.cure`: unknown POSIX error: module_identity_missing
```

So a user who scaffolds an FSM project cannot `cure check` or `cure compile` the FSM file. `cure run` on a standalone file happens to work, which masks the problem. The `examples/cure_exchange/cure/README.md` documents this independently as "limitation #2" — and its author worked around it by hand-writing a duplicate FSM rather than using the generated one. **A language whose flagship concurrency feature cannot be type-checked is a language whose flagship feature is unusable in tooling.**

### 4.2 🔴 Holes do not block code generation

The documentation makes a strong guarantee:

> "Holes are firewalled, not trusted. A `{:hole, name}` term typechecks against any expected type but **blocks codegen: no beam is emitted for a definition that still contains one**." — `docs/KERNEL.md`

I tested this directly:

```cure
mod HoleCall
  use Std.Nat
  use Std.Io
  fn f(n: Nat) -> Nat = ?goal
  fn main() -> Atom =
    let v: Nat = f(Z())
    let _: Unit = Std.Io.println("called the hole!")
    :ok
end
```

```
$ cure run /tmp/hole_call.cure
called the hole!
```

**A reachable, unfilled hole compiles and runs silently.** The documented firewall is not implemented. This is a soundness/workflow gap: the entire point of a typed hole is that it *cannot* be forgotten.

### 4.3 🟠 `@total true` is documented but not implemented

`docs/LANGUAGE_SPEC.md` states: "Add `@total true` to require a successful totality proof at compile time." I tested an obviously non-terminating function:

```cure
@total true
fn down(n: Nat) -> Nat = match n
  Z() -> Z()
  S(k) -> down(S(k))     # recurses on a LARGER argument
```

```
$ cure check /tmp/bad_total3.cure
/tmp/bad_total3.cure: OK
```

The `@total` decorator is **not parsed** — it is absent from the parser's decorator set. Totality is only *enforced* for functions used in types (which does work, per `totality_wiring_test.exs`), but the advertised per-declaration opt-in is a no-op. The docs and implementation disagree.

### 4.4 🟠 God files and god modules

| File | LOC | `def`s |
|---|---:|---:|
| `lib/cure/elab/elaborator.ex` | 16,249 | 1,142 |
| `lib/cure/compiler/parser.ex` | 15,296 | 903 |
| `lib/cure/diagnostic/adapter.ex` | 6,916 | 1,113 |
| `lib/cure/elab/program.ex` | 6,293 | 525 |
| `lib/cure/elab/declarations.ex` | 4,736 | 444 |

Individual functions reach 297 lines (`elaborate_named_call_resolved_unchecked/8`) and 245 lines (`elaborate_match_dispatch/6`). These are merge-conflict magnets and cognitive-overload traps. **398 `rescue`/`catch` sites** and **1,622 catch-all clauses** exist across `lib/`, with **153 `_ ->` fallbacks in `elaborator.ex` alone** — in a compiler where silent degradation is especially dangerous. There are also **81 `IO.inspect`/`dbg` calls** remaining in shipped code.

### 4.5 🟠 Performance: the stdlib is slow to build, and `Std.Actor` dominates

`docs/COMPILER_PERFORMANCE_BASELINES.md` reports (M1 Pro, OTP 29):

- **All 75 sources, cold: 54.6 s** — of which **`Std.Actor` alone is 36.1 s (66%)**.
- Warm total: 3.2 s.

The launch checklist confirms a cold `mix cure.repl` took **~6 minutes**. A 36-second compile for one module is a real developer-experience problem and signals algorithmic issues in elaboration of the macro-heavy actor module.

### 4.6 🟡 Stdlib consistency issues

The subagent audit found concrete inconsistencies:
- **Contradictory `Option`/`Result` BEAM encodings** documented: `core.cure:6` says `{:some, v}`/`{:none}` (lowercase); `option.cure:8` says `{:Some, v}`/`:None` (capitalised). One is wrong — a real Elixir/Erlang interop hazard.
- **Duplicate `@extern`**: `@extern(:string, :split, 3)` declared twice in `string.cure` (lines 285, 297).
- **Inconsistent naming**: `unwrap_ok`/`unwrap_error` (`core.cure`) vs `unwrap` (`result.cure`) vs `unwrap_some` (`match.cure`) — three names for one operation.
- **Inconsistent decorator placement**: `@group`/`@prelude` applied to modules in some files, to types in others.
- `Std.Regex` lives in `lib/std_deps/regex/` rather than `lib/std/`, an inconsistent packaging location.

### 4.7 🟡 Documentation drift

Several docs are marked historical/superseded but remain in the HexDocs extras list (`STDLIB_DEPENDENT_CLAIMS_AUDIT.md`, `DEPENDENT_TYPE_SLICES.md`, `DEPENDENT_KERNEL_PEERNESS_ROADMAP.md`). `docs/LAUNCH-CHECKLIST-0.34.md` openly lists unfinished items (version bump, website redesign, full gate pass). `docs/TUTORIAL.md` still says "five stages: lex, parse, type check, optimise, codegen" — describing the *deleted* classic pipeline. `cure help` advertises ~25 of ~40 subcommands.

### 4.8 🟡 A single-maintainer bus factor

The v0.34.0 blog post credits **Cosmo S. Harbinger (@Qata)** with "almost every major subsystem" — the kernel, NbE engine, erasure, macro engine, and regex infrastructure. `mix.exs` lists a single maintainer. For a 163k-LOC compiler with a soundness-critical kernel, this is a significant project risk.

## 5. Suggestions and a Path Forward

### 5.1 Fix the macro-container tooling gap (highest priority)

This is the single change that most improves the language's usability. Concretely:

1. **Make `cure check` expand and check macro containers.** The `computed by` expander *does* run under `cure run`; the failure is specific to the check path. Route `check_source` through the same expansion the emitter uses, and report the *inner* generated-syntax error rather than a generic `E092`.
2. **Fix `module_identity_missing` in project mode.** A macro module that compiles standalone must compile in a project. This looks like the lifted-module resolution failing to find an owner-qualified identity when `source_paths` is configured.
3. **Add a regression test**: `cure check` and `cure compile` on the `cure new --fsm` / `--app` scaffolds. The fact that this shipped broken means the scaffolds aren't in the CI gate.
4. **Fix the `cure_colony` example** (or its `Cure.toml`) so a shipped showcase compiles.

### 5.2 Enforce the hole firewall

Make `check_codegen_ready/1` (which exists at `program.ex:2207`) actually reject definitions containing reachable holes, and add a test asserting `cure compile` fails on `?goal`. If holes are meant to be permitted in *unreachable* positions, document that precisely and detect reachability.

### 5.3 Implement or remove `@total true`

Either wire the decorator into the parser and the totality closure (the machinery already exists for type-level functions), or remove the claim from `LANGUAGE_SPEC.md`, `LANGUAGE.md`, and `TUTORIAL.md`. A documented no-op is worse than an absent feature.

### 5.4 Decompose the god files

- **`elaborator.ex`** (16k lines) should be split by surface construct: `Elaborator.Call`, `.Match`, `.Lambda`, `.Record`, `.Interface`, etc. The 153 catch-all `_ ->` clauses should be audited and made to fail loudly.
- **`parser.ex`** (15k lines) should split by grammar stratum (declarations / expressions / patterns / macros).
- **`diagnostic/adapter.ex`** (6.9k lines) is pure prose and could be data-driven (a map of code → template) rather than 1,113 functions.
- Replace the 398 `rescue`s with explicit `{:error, reason}` returns where possible; audit each bare `rescue` for swallowed errors.
- Remove the 81 `IO.inspect`/`dbg` calls.

### 5.5 Address the `Std.Actor` compile time

36 seconds for one module is a red flag. Profile the elaboration of `Std.Actor` specifically — the macro expansion and interface-cycle stabilisation are the likely culprits. The baseline doc already names it "the first candidate for measured decomposition." Consider caching expanded macro output keyed by input hash.

### 5.6 Standardise the stdlib

- Pick **one** `Option`/`Result` runtime encoding and fix all docs to match.
- Deduplicate the `@extern(:string, :split, 3)` declaration.
- Unify extractor naming (`unwrap`/`unwrap_ok`/`unwrap_some` → one convention).
- Move `Std.Regex` from `std_deps/regex/` into `lib/std/`.
- Make `@group`/`@prelude` placement a checked invariant, not a convention.

### 5.7 Documentation hygiene

- Remove superseded docs from the `mix.exs` extras list (or move them under `docs/archive/`).
- Update `TUTORIAL.md` §2 to describe the real pipeline.
- Generate `cure help` from the actual command registry so it can't drift.
- Finish the launch checklist items before tagging 0.35.

### 5.8 Strategic opportunities

Beyond fixes, the project has unexploited strengths:

1. **Lean into the "verified concurrency" niche.** The combination of dependent types + typed OTP is unique. A flagship, *working* end-to-end example — a supervised, session-typed, proof-carrying service that compiles and runs — would be far more persuasive than the current examples, several of which don't compile.
2. **Publish the soundness argument.** The kernel is small enough to audit; a mechanised or carefully written soundness proof (the `MATCH.md` Appendix J sketch is a start) would differentiate Cure from every other "dependent types on X" experiment.
3. **Improve the cold-start story.** A precompiled stdlib shipped as a binary artifact (the `priv/ebin` path exists) plus a warm cache would turn a 6-minute first-run into seconds — critical for adoption.
4. **Grow the contributor base.** With 163k LOC, 6,350 tests, and excellent docs, the project is *ready* for contributors; the god files and single-maintainer concentration are the main barriers. A `CONTRIBUTING.md` with a "good first issue" list and a decomposition plan would help.

---

## 6. Verdict

Cure is an **impressively ambitious and largely successful** research-grade language. The dependent kernel is real, sound in the cases I tested, and well-engineered. The self-hosted stdlib contains genuine proofs. The OTP-as-macros architecture is elegant. The test and verification infrastructure (Antigen, the Idris oracle) is exceptional.

Its weaknesses are of two kinds. The **engineering-debt** kind — god files, error-swallowing, stdlib inconsistencies — is normal for a project of this size and is tractable. The **correctness-of-claims** kind is more concerning: holes that don't block codegen, `@total true` that does nothing, and macro containers that can't be type-checked are all cases where the documentation promises more than the implementation delivers. In a language whose entire value proposition is *"the compiler proves things,"* a gap between claimed and actual guarantees is the most damaging kind of bug.

The good news: every one of these gaps is fixable, the fixes are well-scoped, and the underlying machinery already exists. Cure is perhaps two focused release cycles of hardening away from being a genuinely trustworthy dependently-typed language for the BEAM.
